# Cupertino Rule-Based Styling Prototype

This repository is a working prototype for a rule-based styling and theming system in Flutter's Cupertino library. It accompanies the design proposal in [`quick-version.md`](quick-version.md), which outlines the motivation, core design skeleton, and FAQ. Detailed design documents will be added under a `docs/` directory at the repository root as the proposal evolves.

To give the prototype a concrete visual baseline for pixel-level regression testing, the `Button` and `Switch` widgets in this repository borrow the current visual specifications of `CupertinoButton` and `CupertinoSwitch` from `cupertino_ui`. The widgets intentionally omit the `Cupertino` prefix because this proposal targets the upcoming Liquid Glass component library (`cupertino`) rather than retrofitting legacy `Cupertino*` widgets in place.

## Reading the Code

The package implementation lives under `lib/src/` and is split into four layers.

The core rule engine in `lib/src/engine/` (`engine.dart`, `composite.dart`, `groups.dart`, and `cache.dart`) defines conditions (`Condition`), style payloads (`Style`), sources (`DeriveSource`: a literal value, a reference to another field of the same component or to a global `Token`, a callback, a Color transform of another source (opacity, opaque), or some sub-properties of a composite field (parts)), and token groups (`TokenGroup`). It knows nothing about Cupertino types and, except for `GroupTokenMixin.of(context)` in `groups.dart` (which calls into the widget layer), nothing about Flutter widgets; it evaluates a flat chain of rules against a state map, resolving properties per field on a last-write-wins basis and evaluating derived values after the entire chain finishes. A callback (a computed source) is the general form of a derive: a function placed in one field's slot that reads the instance's other final values and the tokens at the same state through a lazy, memoized view (`StyleView`; cycles through callbacks and field references throw a `RuleError` naming the cycle). It runs when tokens are bound and its result is cached with the other bound values. A `LegacySource` is the bridge for legacy `WidgetStateProperty` closures on flat parameters: it may return null to fall through to earlier rules, and values that depend on it are re-evaluated on every lookup instead of being cached. The engine handles only `DeriveSource`, which stores every kind in the same fixed slots and implements `==` / `hashCode` once; the typed, per-component classes described below are constructor-only subclasses. A theme animation (`Tokens.lerp`) lerps every token on its two resolved values: the token's own `lerp:`, else by value type, else a switch at t = 0.5.

The Flutter widget binding in `lib/src/widgets.dart` connects the rule engine to the widget tree. `StyleTheme` sits at the root of the application and holds global token groups and component rules, while `StyleScope` appends local rule overrides for a subtree. Internally, `StyleNode` and `ChannelLink` form a persistent linked list of rules partitioned by component type (`RuleChannels`) and cached per `(StyleNode, ResolvedEnvironment)`. Updating rules for one component type notifies only widgets subscribed to that channel, and `StyleTheme.captureAll` preserves scoped rules across modal routes such as dialogs and action sheets.

The Cupertino adapter in `lib/src/cupertino_adapter.dart` (along with the generated-style token interface in `lib/src/cupertino_adapter.facade.g.dart`) bridges Cupertino's environment model into the rule engine. It defines the three environment dimensions (`brightness`, `highContrast`, and `interfaceLevel`), has the built-in tokens as statics on the generated library-owned interface `CupertinoToken<T>` over a generated private enum (the group `cupertinoTokenGroup`), takes their library defaults from the default `CupertinoThemeData` (`cupertinoDefaultTokens`, a `CupertinoTokenRule`), uses the generated token rule class `CupertinoTokenRule` (a `TokenSourceRule` with a flat-value constructor and `.derive(...)`), defines the token-layer sources (`CupertinoTokenSource<T>` / `CupertinoTokenColorSource`, taken by `token.setFrom(...)`), and provides `cupertinoEnvSplitter`. The group also has one derived token, `CupertinoToken.tintedFill` (primary at opacity 0.12 in light mode and 0.26 in dark mode), set by two brightness-conditioned token rules (`cupertinoDefaultTokenRules`), so the tinted button default stays one rule without environment conditions. Whenever a rule or constructor parameter contains a `CupertinoDynamicColor`, the splitter expands that rule at chain-construction time into environment-conditioned plain-color sub-rules. By the time a widget resolves its style, no unexpanded `CupertinoDynamicColor` remains, eliminating manual `CupertinoDynamicColor.resolveFrom` calls inside widget implementations. This file also defines a sample custom token group (`enum Brand<T> with GroupTokenMixin<T>` with `Brand.group`, whose tokens implement only the engine's `Token<T>`, and `BrandRule`, the `TokenValueRule` an app without code generation writes by hand, with the presets `BrandRule.teal` / `BrandRule.purple` as const rule lists), the helper that expands map-backed `WidgetStateProperty.fromMap` values into rules, and `WidgetStatePropertyRule`, which turns any other `WidgetStateProperty` (such as `resolveWith`) into one legacy rule resolved with the widget states the original widget passes for that property.

The prototype components live in `lib/src/button.dart` and `lib/src/switch.dart`, paired with their hand-written codegen counterparts `lib/src/button.g.dart` and `lib/src/switch.g.dart` (marked `SHOULD BE GENERATED`). Each `.dart` file declares the component's typed field enum (`enum ButtonField<T extends Object> { foregroundColor<Color>(), padding<EdgeInsetsGeometry>(), ... }`), expresses the built-in appearance table as a `const` list of rules (`buttonDefaults` and `switchDefaults`), translates flat constructor parameters (`color`, `foregroundColor`, `activeTrackColor`, etc.) into call-site rules placed before `states:`, and builds the widget from the resolved `ButtonStyle` or `SwitchStyle`. Each `.g.dart` file defines the typed `When`, the source classes (`ButtonSource<T>`, `ButtonColorSource`, and one class per composite type: `ButtonTextStyleSource`, `ButtonIconStyleSource`, `ButtonBorderSideSource`), the callback view (`ButtonView`), the rule payload `ButtonStyleSpec` with its all-values form `ButtonStyle`, and `ButtonRule` with `.when` / `.always` / `.whenAny` (and the same for Switch, which has no composite fields), along with one region constructor per field whose default is partitioned (`ButtonRule.backgroundColor(tintedEnabled: ..., tintedDisabled: ...)`, `SwitchRule.trackColor(selected: ...)`, ...): each named argument is one region of that field (the states where one library default rule sets it), so a value replaces exactly that default.

## The Derive API

A rule has one payload, `style:`, typed `ButtonStyleSpec`. Rules for one component can share a typed list spread, so the component name is written once:

```dart
StyleTheme(rules: <Rule>[
  ...<ButtonRule>[
    .when(appearance: {.tinted}, style: .derive(
      backgroundColor: .opacity(.fromField(.foregroundColor), 0.2),  // a transform of a field
      foregroundColor: .fromCustomToken(Brand.accent),               // an app token (Token<Color>)
      focusColor: .computed(myFocusRing),                            // Color myFocusRing(ButtonView s)
      padding: .value(.all(8)),                                      // a literal
      textStyle: .parts(color: .fromToken(.primaryColor)),           // one sub-property
    )),
    .when(pressed: true, style: .values(backgroundColor: CupertinoColors.systemRed)),
    .always(style: .derive(side: .parts(color: .opacity(.value(CupertinoColors.systemGreen), 0.5)))),
    .backgroundColor(tintedEnabled: CupertinoColors.systemIndigo),   // a region constructor
  ],
  CupertinoTokenRule(primaryColor: CupertinoColors.systemPurple),
  Brand.pressedAccent.setFrom(.opacity(.fromCustomToken(Brand.accent), 0.5)),
], child: ...)
```

- **Rule entry points.** `.when(...)` takes the condition's dimensions as named parameters, `.always(...)` has no condition, `.whenAny([ButtonWhen(...), ...], ...)` matches any of several conditions, and the region constructors (`.backgroundColor(tintedEnabled: ...)`) take values only. The full-name form `ButtonRule(ButtonWhen(...), style: ...)` is kept; it is `==` to the `.when(...)` rule with the same dimensions.
- **Payload.** `.values(...)` is a const redirect to `ButtonStyle` (plain values only); `.derive(...)` takes sources. `ButtonStyle(...)` and `ButtonStyleSpec(...)` work too. Typed getters exist only on `ButtonStyle`, which is also the resolved result. A rule that mixes values and derives wraps the values in `.value(...)`, or is split into a `.derive` rule and a `.values` rule under the same condition. Equivalent spellings resolve identically but need not be `==`; the same code is `==` and const-canonicalized, so rebuilding with unchanged rules rebuilds nothing.
- **Sources.** `.value(x)`, `.fromField(.x)`, `.fromToken(.x)` (a `CupertinoToken<T>`), `.fromCustomToken(Brand.x)` (any `Token<T>`) and `.computed(fn)`. The parameter types fix the field enum, the token interface and the view type, so a field, token, callback result or value of another type, or a field of another component, is a compile-time error (`test/type_safety_test.dart` checks this with the analyzer).
- **Color transforms.** Every Color slot is typed `ButtonColorSource`, which adds `.opacity(source, x)` and `.opaque(source)`; other slots keep `ButtonSource<T>`, so a transform there does not compile. `.opacity` multiplies: the result's alpha is `clamp(sourceAlpha * x, 0, 1)`, so a translucent source keeps its translucency, a factor above 1 raises the alpha up to opaque, and a fully transparent source stays transparent. `x` must be finite and >= 0 (assert). `.opaque` sets alpha to 1 and keeps the color channels, also for a fully transparent source; the filled button default uses it on primary, like the original's `withOpacity(1.0)`. Transforms wrap any color source and nest: `.opacity(.opaque(x), 0.5)` is x at 50%, and `.opacity(.value(CupertinoColors.systemRed), 0.5)` is the const way to write a translucent dynamic color (the literal is expanded per environment).
- **Composite fields** (`textStyle`, `iconTheme`, `side`) take their own source class: a whole value (`.value`, `.fromToken`, ...) or `.parts(...)`, which sets only the given sub-properties (color ones so far, each typed `ButtonColorSource`). Each part competes under "last rule wins" on its own; the other properties keep what earlier rules produced. There is no `base`: "whole plus parts" is two rules, which resolves like the previous single-rule form. `.parts()` with no argument fails an assert (a compile error in a const context). `BorderSide` is an atomic value; `side: .parts(color: x)` changes only the color of the side the earlier rules produced. The icon field still uses `IconThemeData` as its value type; the design calls for the Icon component's own `IconStyle` there, and its source class already has the planned name `ButtonIconStyleSource`.
- **Per-environment opacities** live in the token layer: the tinted button background reads `CupertinoToken.tintedFill`, which two token rules derive from primary per brightness. Library defaults still contain no environment-conditioned color derive (checked by `test/regions_test.dart`).
- **Callbacks** take a `ButtonView`, an extension type over the engine's `StyleView` with `s.field(.x)`, `s.token(.y)` and `s.customToken(Brand.z)` plus the state getters. Reads are lazy and memoized per state; a cycle throws a `RuleError` naming it. Use top-level or static functions: their tear-offs are constants, while an inline closure is a new object on every build and defeats change detection.
- **Provenance and errors** (`StyleResolver.debugSources`, `RuleError`) use the same words: `field .foregroundColor`, `token primaryColor`, `custom token accent`, `computed rule #n`, `(opacity 0.5)`, `(opaque)`, `parts(color: ...)`.

### Token rules and reads

- **Token groups** are enums: `enum Brand<T extends Object> with GroupTokenMixin<T> { accent<Color>(), ...; const Brand({this.lerp}); final T? Function(T?, T?, double)? lerp; static const TokenGroup group = TokenGroup('Brand', values); }`, registered with `StyleTheme(groups: [Brand.group])`. There is no data class for a whole group: a preset is a const rule list (`BrandRule.teal`), and a whole-group read is a Record of single reads.
- **Token rule classes** set some tokens: one typed, optional parameter per token, and only the given ones are set. `TokenValueRule` takes plain values (override `values`); `TokenSourceRule` takes sources (override `sources`; `.value(x)` literals are split from derives by the base class). `CupertinoTokenRule` is generated on `TokenSourceRule` with a flat-value constructor (`CupertinoTokenRule(primaryColor: purple)`, which leaves `tintedFill` deriving from the new primary) and `CupertinoTokenRule.derive(tintedFill: .opacity(.fromToken(.primaryColor), 0.2))`. `BrandRule(accent: ...)` is a hand-written `TokenValueRule`. All are const, and a wrong value type is a compile-time error.
- **One token**: `Brand.accent.set(color)`, or `Brand.pressedAccent.setFrom(.opacity(.fromCustomToken(Brand.accent), 0.5))` for a reference to another token (`.value`, `.fromToken`, `.fromCustomToken`; Color tokens also `.opacity` / `.opaque`). The receiver fixes the value type, so `Brand.accent.set(3)` does not compile. These are method calls, so not const, but equal code gives `==` rules. There is no generic `TokenRule.value(token, value)`: type inference would widen it to `Object` and accept `TokenRule.value(Brand.accent, 3)`. The untyped engine form `TokenRule.raw(when, values: {...}, derive: {...})` remains for hand-written engine code; its types are only checked when the chain is built.
- **Reads**: `Brand.accent.of(context)` (and `CupertinoToken.primaryColor.of(context)`) returns a non-null `Color`; inside the engine, `tokens.read(Brand.accent)`. A token of a group that is not registered throws a `RuleError` naming the group's enum and the token. Every token must have a default in every environment; `debugMissingTokenDefaults(tokens)` lists the gaps (a test runs it for the library and the sample app group), and reading an unset token throws a `RuleError`.
- **Theme animation**: `Tokens.lerp(a, b, t)` lerps token by token on the two resolved values through `token.lerpObject`: the token's own `lerp:` (e.g. `discrete`, or a composite's static lerp), else the built-in table (`Color`, `double`, `TextStyle`, `EdgeInsetsGeometry`, `BorderRadiusGeometry`, `AlignmentGeometry`, `Size`, `Offset`, `ShapeBorder`, `BorderSide`, `IconThemeData`, `List<BoxShadow>`, `List<Shadow>`), else a switch at t = 0.5. A derived token lerps its two final values (tintedFill animates its alpha continuously across a light-to-dark change), and a token pinned on one side lerps against the other side's value.

### Padding and text scale

Padding that follows the text scale (Material's buttons shrink it as the text grows) is two plain fields: `padding`, the padding at a text scale of 1, and `paddingScaler`, the policy. `PaddingScaler.identity()` keeps the padding (the Cupertino default), `.stops([(1, 1), (2, 0.5), (3, 0.25)])` multiplies it by a factor per text scale (Material 3), and `.absolute([(2, ...), (3, ...)])` gives fixed paddings per scale (Material 2's icon buttons). The widget calls `paddingScaler.apply(padding, textScaler, fontSize)` at layout; the text scale is measured on the resolved font size. Both fields are data, so overriding one keeps the other, and `paddingScaler: .identity()` turns scaling off. The stops are lists of records because a const map can't have `double` keys.

Flat constructor parameters and legacy `WidgetStateProperty` values (legacy rules on theme and flat parameters) work as before.

## Exploring the Interactive Demo

The `example/` directory contains an interactive app (`example/lib/main.dart`) with a top control bar for switching between Light and Dark mode, Standard and High Contrast, and custom `Brand` token palettes (`teal` and `purple`). Below the control bar, five sections demonstrate the core mechanics of the proposal:

1. **Call site**: Passes dynamic colors and `WidgetStateProperty.fromMap` values directly to `Button` and `Switch` constructors (including properties where legacy `cupertino_ui` fails to resolve dynamic colors), and tweaks only the pressed state on a single button via `states:`.
2. **Global theme + local scope + dialog**: Combines app-wide `StyleTheme` rules (`Brand` token derivation and a combined dark + pressed rule) with a local `StyleScope` override that changes only the background color while preserving the theme's corner radius and dark-pressed foreground, plus a dialog launched via `StyleTheme.captureAll` that inherits the caller's scope chain.
3. **Derive**: Shows icon and text colors automatically following the final resolved `foregroundColor` across themes and call sites, alongside a button where a plain rule intentionally breaks that follow relationship for the icon only.
4. **Channel isolation**: Displays live widget build counters for `Button` and `Switch` inside a `StyleScope` while you mutate `ButtonRule` vs. `SwitchRule` entries independently, showing that changing one component's rules rebuilds only widgets of that component type.
5. **Region rules**: A `StyleScope` restyles the tinted enabled and disabled regions with `ButtonRule.backgroundColor` / `foregroundColor` while the filled button (another region) keeps the theme look, refines the enabled region with a later rule written with a finer condition (pressed), and restyles switches per region (`SwitchRule.trackColor` / `thumbColor` / `opacity`); outside the scope, `states:` sets a single region of one button and one switch.

## Reading the Tests

The test suite under `test/` and `example/test/` verifies both behavioural equivalence with `cupertino_ui` and the new capabilities described in the proposal:

- `test/quick_version_snippets_test.dart` translates every code snippet and FAQ claim in [`quick-version.md`](quick-version.md) into executable assertions across all 8 environments and all button/switch states.
- `test/compare_original_test.dart` renders the prototype `Button` and `Switch` alongside the original `cupertino_ui` widgets and compares their captured pixels across 288 default button cases (3 appearances × 3 sizes × 4 interaction states × 8 environments), 160 default switch cases (2 values × 2 enabled states × 5 interactions × 8 environments), and flat constructor parameter overrides.
- `test/original_bugs_test.dart` reproduces the 10 unexpanded `CupertinoDynamicColor` bugs in the original `CupertinoButton` and `CupertinoSwitch` implementations and verifies that the rule-based widgets resolve every slot to the expected dark/high-contrast/elevated variant.
- `test/original_checkbox_bugs_test.dart` confirms on the original `CupertinoCheckbox` that user-supplied dynamic colors passed to `fillColor` (checked and unchecked), `checkColor`, `activeColor`, and `focusColor` render with their light-mode variant in dark mode.
- `test/dynamic_color_test.dart` tests `cupertinoEnvSplitter` directly: deduplicating identical variants, intersecting with existing `When` conditions, handling sub-property colors (`textStyle.color`, `iconTheme.color`, `BorderSide.color`), opacities on dynamic tokens (token rules written with `setFrom(.opacity(...))`), the per-brightness `tintedFill` token, provenance wording, and caching expanded chains.
- `test/widgets_test.dart` covers `StyleTheme` and `StyleScope` mechanics: rule ordering, per-channel rebuild isolation, `StyleTheme.captureAll` across pushed routes, `CupertinoApp` bridge integration, and `WidgetStateProperty.fromMap` expansion (the expansion helpers reject `resolveWith` closures).
- `test/regions_test.dart` checks the region tables behind the region constructors against the library defaults (one region per default rule, one field without a constructor per single region), checks every constructor's names, doc lines, parameters and value slots against the tables and the naming function, and tests region rules themselves: const lists, expansion into engine rules, equality, rejection of `WidgetStateProperty` values, and equivalence with rules written with the region conditions.
- `test/derive_api_test.dart` covers the derive API: the spellings of "mostly values, one derive" (one `ButtonStyleSpec` with `.value`, a spec rule plus a `ButtonStyle` rule, region constructors plus a derive rule, and the `.when` / `.derive` / `.values` versions) resolving identically in all 576 button minterms and comparing `==` where the code is the same rule; `.when` / `.always` / `.whenAny` in a typed spread against the full-name rules (Button and Switch); const canonicalization and no rebuild for equal non-const rules (token rules included); `.opacity` (translucent field, token and dynamic-literal sources, factors above 1, transparent sources, the infinite / NaN / negative assert) and `.opaque` (translucent and transparent sources, `.opacity(.opaque(x), 0.5)`, the filled default); `.parts` split over two rules against the previous whole-plus-parts single engine rule in all minterms, parts across rules, `side: .parts(...)`, the empty-`.parts()` assert; callbacks reading fields and tokens; provenance wording; and app tokens through `.fromCustomToken` with transforms.
- `test/token_layer_test.dart` covers the token layer: `CupertinoTokenRule(primaryColor: ...)` leaving `tintedFill` derived in every environment, `BrandRule`, the flat-value and `.derive` constructors of `CupertinoTokenRule`, a hand-written `TokenSourceRule`, `set` / `setFrom` with `.opacity` / `.opaque`, non-null typed reads (`tokens.read`, `token.of(context)`, a Record of reads), the error for an unregistered group, the every-token-has-a-default check, and the per-token theme animation (tintedFill across light to dark, a token pinned on one side, a token's own `lerp:`, the built-in table).
- `test/type_safety_test.dart` runs the analyzer on the snippets under `test/fixtures/type_errors/` (excluded from `flutter analyze`) and expects an error on each marked line: `.opacity` / `.opaque` on a non-Color slot, a Color field in an EdgeInsets slot, a wrong type inside `.parts`, an empty `.parts()` (const assert), a library or custom token of the wrong type, `Brand.accent.set(3)` and `BrandRule(accent: 3)`, a callback with the wrong return type, a `.value` / `.values` of the wrong type, and a field of another component. `test/fixtures/type_ok.dart` is the correctly typed control.
- `test/callback_rule_test.dart` covers callbacks (`.computed`) at theme level and call site: chains through token references, other callbacks, field references and sub-property targets; cycle errors; region and shadowing analyses; provenance; const canonicalization with a static tear-off versus an inline closure that defeats change detection; theme and environment changes; and the focus ring written as a theme callback (`defaultButtonFocusColor`) giving the default pixels.
- `test/parts_over_derived_test.dart` covers `.parts` over a whole value that is itself derived: a `BorderSide` from a callback that depends on the state and the foreground (`.parts(color:)` and `.parts(width:)` keep the rest following the callback in every environment and state, a derived part over the derived whole, two patches, a derived whole after a patch replacing it, theme whole plus `states:` patch, provenance), and a `TextStyle` from a token (patched color with size and weight from the token, a changed token keeping the patch, and order: a token after a patch always wins because a token is never partial, a callback whole without a color keeps the patch).
- `test/padding_scaler_test.dart` checks `PaddingScaler` against Material's `ButtonStyleButton.scaledPadding` (M3 proportional, M3 directional icon variant, M2 non-proportional icon variant in both text directions), a nonlinear text scaler measured on the font size, and the fields in rules: the `.identity()` default, a theme setting both, the unscaled resolved style, overriding `padding` keeping the scaler, `.identity()` in a later rule, dot shorthands, and value equality.
- `test/legacy_widget_state_test.dart` covers `resolveWith` values on `Switch.trackOutlineColor` / `trackOutlineWidth` / `mouseCursor` and `Button.mouseCursor`: the widget states passed per property, pixel and cursor equivalence with the original widgets across states and environments (with one listed expected difference, a null width), fall-through of null to the theme and defaults, per-environment resolution of dynamic colors, and re-evaluation of an impure closure on rebuild while the rest of the cache is reused.
- `example/test/demo_test.dart` tests all five sections of the interactive example app.
