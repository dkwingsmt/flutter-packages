# 2. Problems with the Current Model

[← Previous: 1. Context & Scope](01-context-and-goals.md) | [Table of Contents](00-intro.md) | [Next: 3. Goals & Existing Options →](03-requirements-and-existing-options.md)

---

`ThemeData`, `WidgetStateProperty`, and `CupertinoDynamicColor` have run in production for years. Anyone who has maintained `material_ui` or `cupertino_ui` knows that a large share of day-to-day styling and theming bugs stem from **missed updates across multiple hand-maintained files**. For readers unfamiliar with the internals of these two libraries, here are three recurring patterns from the source code and issue tracker:

- **Widget parameters and theme fields routinely drift apart**: Although `material_ui` introduced a token-based code generator (`gen_defaults`) to generate 87 private `_XDefaultsM3` default classes, code generation stops at the default classes themselves. Every time a developer adds a customizable property, they still have to manually update up to 9 places: the widget constructor, `XThemeData` (or `ButtonStyle` / `styleFrom` for buttons), `_XDefaultsM3`, `copyWith`, `merge`, `lerp`, `hashCode`, `==`, and `debugFillProperties`. Missing any one of these creates API gaps. For example, `CircularProgressIndicator` supported `strokeWidth` and `borderRadius` for over a year before `ProgressIndicatorThemeData` caught up ([#131690](https://github.com/flutter/flutter/issues/131690)). The `TextField` constructor has always offered a `style` parameter for input text, yet `InputDecorationTheme` still lacks a corresponding field ([#118267](https://github.com/flutter/flutter/issues/118267)). Conversely, `InputDecorationThemeData` gained `activeIndicatorBorder` and `outlineBorder` during the Material 3 migration, while `InputDecoration` itself never added those parameters.
- **Equality, merging, and cross-route inheritance boilerplate are inconsistent**: In `cupertino_ui`, `NoDefaultCupertinoThemeData` originally omitted `==` and `hashCode` altogether. Setting `cupertinoOverrideTheme` caused every equality check to return `false`, triggering broken theme interpolation animations and dozens of unnecessary rebuilds ([#165455](https://github.com/flutter/flutter/issues/165455)). When a later fix added `NoDefaultCupertinoThemeData.==` by hand, it missed the `selectionHandleColor` field included in the superclass `CupertinoThemeData.==` (`theme.dart:582-608`). Among the 52 local theme widgets (`XTheme`) in `material_ui`, 8 (including `ChipTheme`, `SliderTheme`, and `ToggleButtonsTheme`) extend plain `InheritedWidget` instead of `InheritedTheme`, causing local themes to vanish when opening a dialog or pushing a new route. `BottomSheetTheme` has no corresponding local theme widget at all, and `InputDecorationTheme` has at least 4 incompatible inheritance and merging implementations across different widgets ([#131666](https://github.com/flutter/flutter/issues/131666)).
- **Branches inside the same widget forget to resolve dynamic values**: In `CupertinoSwitch.build`, `activeTrackColor` calls `CupertinoDynamicColor.resolve` on the default color branch (`switch.dart:721`), but skips environment resolution a few dozen lines later on the user-supplied branch (`_widgetTrackColor`, `switch.dart:751`). As a result, a dynamic color passed by a user always renders its light-mode value in dark mode.

Looking at these examples, a natural question arises: **Since `gen_defaults` has already proven the value of code generation in `material_ui`, can the problem be solved simply by expanding the code generator to emit all 9 pieces of boilerplate?**

Expanding code generation is indeed the right way to eliminate hand-syncing omissions—this design embraces that direction and extends code generation across the entire styling system. However, a closer look at the source code shows that hand-syncing bugs are only a symptom. Even if a generator produced every line of boilerplate and AI agents assisted with coding and code review to eliminate trivial omissions and sync mistakes, keeping the underlying `XThemeData` + `WidgetStateProperty` + `CupertinoDynamicColor` model leaves three structural bottlenecks that code generation or review alone cannot fix: **multi-dimensional state representation and equality**, **overloaded `null` fallbacks and broken interpolation**, and **opaque eager derivations alongside runtime and binary-size overhead**.

## 2.1 Problem 1: Patching Multi-Dimensional State onto a 1D Static Property List Makes Evolution Expensive and Local Overrides Fragile

From the start, the existing architecture in Material and Cupertino was built on top of a **one-dimensional static `property → value` list**, and never treated states and environment dimensions as first-class citizens of the model. When a component's appearance needs to vary by interaction state or brightness/contrast environment, the lack of a dedicated structural layer for condition dimensions forces the framework to keep the 1D property list skeleton intact and patch around existing properties either **horizontally (splitting flat parameters)** or **vertically (wrapping individual property types—`WidgetStateProperty<T>` (`WSP`) for interaction states in Material, and `CupertinoDynamicColor` (`CDC`) for brightness, contrast, and elevation in Cupertino)**.

This vertical "per-property state wrapper" approach carries a contagious **function coloring** effect. Much like making a leaf function `async` in Dart forces every caller up the chain to return `Future<T>`, once a leaf property needs to support a new dimension, its type must widen from `Color?` to `WidgetStateProperty<Color?>?` (and if it must carry both interaction state and environment brightness without losing information prematurely, its true type must nest further into `WidgetStateProperty<CupertinoDynamicColor?>?`), cascading signature changes through constructor parameters, theme fields, `copyWith`, `lerp`, `merge`, local variables, and internal helper methods along the entire evaluation pipeline. If a component wraps every property upfront like `ButtonStyle` does, callers must wrap every static value they pass in `WidgetStatePropertyAll(...)`. A scan of over 4,200 style definition files across dozens of large production Flutter apps and component libraries found that 69% of files using `WidgetStateProperty` directly (520+ files) only call `.all()` or `WidgetStatePropertyAll` to wrap static constants like `padding`, `shape`, and `minimumSize` that never change with interaction state. To spare callers that everyday ceremony, the framework leaves properties on most other widgets as plain types and upgrades them one by one as feature requests arrive. For instance, only a few recently updated fields on `TabBar` (`overlayColor`, `dividerColor`) accept `WSP`, while the rest remain plain types; `CupertinoButton` has zero `WSP` properties and relies on two horizontally split flat parameters—`disabledColor` and `pressedOpacity`—to hard-code its disabled and pressed states.

To avoid forcing callers to write nested wrapper types at call sites or rewriting function signatures across internal pipelines, the framework repeatedly compromised between horizontal and vertical patches, accumulating two kinds of technical debt:

The first is **horizontally split fields coexisting with twin parameters**. Components initially unroll specific states into flat parameters and later bolt on vertical `WSP` parameters when more state dimensions are requested: in `material_ui`, `Checkbox` keeps both `activeColor` / `checkColor` and the `WSP`-based `fillColor`; `Switch` keeps `activeColor`, `activeTrackColor`, `inactiveThumbColor`, and `inactiveTrackColor` alongside `thumbColor` and `trackColor`; `Chip` keeps `backgroundColor` and `selectedColor` alongside `color`; and `Radio` keeps `activeColor` alongside `fillColor`. Each pair requires custom precedence rules, making it hard for users to tell from the constructor signature which parameter wins when both are provided.

The second is **disguising multi-dimensional wrappers as subclasses of plain `Color`**. To let callers pass values without an outer wrapper and stop vertical type contagion, `WidgetStateColor` and `CupertinoDynamicColor` directly implement `Color`. The cost is silencing the type system: the compiler can no longer distinguish an already-resolved plain `Color` from an unresolved dynamic color. Whenever an intermediate step is typed as `WidgetStateProperty<Color?>` or assigned to a `Color` local variable, the compiler issues zero warnings while unresolved dimensions are silently dropped as values are passed along or manipulated.

In real-world customization, both per-property patching approaches expose deeper flaws:

### On the Material Side: Single-Property Isolation, Broken Equality, and a One-Size-Fits-All Enum

Customizing stateful styles in Material with `WidgetStateProperty`—whether via `resolveWith` closures or the `WidgetStateProperty.fromMap` constructor introduced in Flutter 3.22—hits three structural limitations that local patches cannot fix:

1. **Splitting state logic by property duplicates conditions, and any derived calculation forces a fallback to opaque closures (breaking `const` and `==`)**: Because `WSP` hangs off individual properties rather than a style block, any state or variant that coordinates multiple properties forces developers to repeat the same condition under every property. This happens whenever an interaction or semantic state (`disabled`, `selected`, `focused`) adjusts 2 to 4 color and stroke properties (background, foreground, icon color, border side) together, or when an appearance or size variant changes 5 to 8 properties (colors, corner radius, padding, minimum size) at once. Instead of declaring "apply this group of styles under this condition," authors must duplicate the condition check across each property. The scan of 4,200+ production styling files confirms this pain point: over 82% of button styling code (roughly 3,470 files) uses helpers like `ElevatedButton.styleFrom` to avoid writing `WSP` by hand, specifically because `styleFrom` splits the `disabled` state under the hood across the independent `WSP` instances for `backgroundColor`, `foregroundColor`, and `iconColor`. As soon as requirements go beyond what `styleFrom` hard-codes—such as setting a `disabled` border `side`, responding to the `selected` state, or theming widgets like `Switch` or `NavigationBar` that lack a `styleFrom` helper—the duplication returns immediately. In components that use `fromMap` to configure the `selected` state, the identical `{WidgetState.selected: ..., WidgetState.any: ...}` map structure is repeated an average of 3 to 4 times in a row within the same widget. In one enterprise button library supporting multiple appearances and sizes (5 types × 5 sizes × toggleable states), `ButtonStyle`'s per-property isolation forced maintainers to write 5 separate `WidgetStateProperty` subclasses (230+ lines of boilerplate) that copy-pasted the exact same three-level `disabled -> togglable -> selected -> switch(type)` branching logic 5 times. Furthermore, although Flutter added the declarative `WidgetStateProperty.fromMap`, it accounts for less than 2% of `WSP` usage in the scanned production code (98% still use `resolveWith`). One key reason is that `fromMap` can only hold precomputed static values, whereas real-world themes and widget defaults (such as `styleFrom` and the 87 `_XDefaultsM3` classes) routinely compute state branches dynamically from tokens or sibling properties (for example, "pressed ripple color = current `foregroundColor` at 10% opacity," or "disabled color = `onSurface` at 12% opacity"). Whenever a branch involves such a derivation, single-property `fromMap` cannot express it, forcing authors back to hand-written `resolveWith` closures. In Dart, two closure instances are never `==` even if their logic is identical. A single inline `resolveWith` in a theme causes `ThemeData ==` to return `false` every time an ancestor widget rebuilds and constructs a new `ThemeData`, triggering unnecessary rebuilds across the entire subtree and even spurious theme interpolation animations in `MaterialApp` ([#89127](https://github.com/flutter/flutter/issues/89127), [PR #154695](https://github.com/flutter/flutter/pull/154695)).
2. **A single global `WidgetState` enum is both too broad for simple widgets and too narrow for complex ones**: `WSP` hard-codes its input to the 8-value `WidgetState` enum shared across the `widgets` package. This one-size-fits-all enum fails at both ends. For simple widgets like `Switch` or `ProgressIndicator`, 8 states are overkill, and nothing in `WidgetStateProperty`'s type signature tells callers which states the widget actually honors—writing a `WidgetState.error` or `scrolledUnder` branch for a `Switch` compiles cleanly but never fires at runtime. At the same time, component-specific states and variants—such as a tristate `Checkbox`'s indeterminate state (`value: null`, which currently piggybacks on `WidgetState.selected`), button appearance variants (`filled`, `tonal`, `outlined`, `text`), or the new size and shape tiers in M3 Expressive (`small`, `medium`, `large`)—do not belong in a global `WidgetState` enum. Because the style layer cannot express component-specific variants, Material is locked into a rigid 1-to-1 binding between widget classes and `XThemeData` classes. Not only does this split buttons into four separate widget classes (`ElevatedButton`, `FilledButton`, `OutlinedButton`, `TextButton`) and four identically structured `XButtonThemeData` classes—meaning that switching a button from filled to outlined based on state requires swapping the widget type and losing subtree `State`—it also makes any variant implemented as a named constructor impossible to theme separately, including `FilledButton.tonal` ([#118063](https://github.com/flutter/flutter/issues/118063), 33 👍), `IconButton`'s `filled` / `filledTonal` / `outlined` variants ([#123829](https://github.com/flutter/flutter/issues/123829)), and `Card.outlined` ([#178611](https://github.com/flutter/flutter/issues/178611)).
3. **Local `XTheme` widgets replace outer configurations wholesale**: Across the 52 `XTheme` widgets, almost every `XTheme.of(context)` implementation (such as `CheckboxTheme.of` and `IconButtonTheme.of`) returns only the nearest `XThemeData` without merging it with ancestor themes. For example, if an app enables M3 Expressive styling in its global `ThemeData.iconButtonTheme` and a developer wraps a subtree in an `IconButtonTheme` just to tweak the icon color, every other unspecified field in that local `IconButtonThemeData` becomes `null`, bypassing the global theme and falling all the way back to standard M3 defaults—silently wiping out the M3 Expressive styling inside that subtree.

### On the Cupertino Side: Flat-Parameter Unrolling, Environment Slots Tied to `Color`, and Disconnected Two-Stage Resolution

`CupertinoDynamicColor` (`CDC`) packs three environment dimensions—`brightness`, `highContrast`, and `interfaceLevel` ($2 \times 2 \times 2 = 8$ slots in total)—into an object that implements `Color`. Consider how this interacts with interaction states on `CupertinoSwitch`'s constructor signature:

```dart
const CupertinoSwitch({
  ...,
  Color? activeTrackColor,
  Color? inactiveTrackColor,
  Color? thumbColor,
  Color? inactiveThumbColor,
  Color? focusColor,
  WidgetStateProperty<Color?>? trackOutlineColor,
  WidgetStateProperty<double?>? trackOutlineWidth,
})
```

In Cupertino, a property often needs `CDC` to respond to brightness and contrast while also using `WidgetStateProperty` (`WSP`) to respond to interaction states. Facing those two sets of dimensions, the existing property model leaves only two choices: **either write a single-layer wrapper (using only `CDC` or only `WSP`), or write the true nested type `WidgetStateProperty<CupertinoDynamicColor>`**. Both paths hit structural dead ends:

1. **If a property uses only a single layer (`CDC` only or `WSP` only), unrolling flat parameters by state does not scale, while not unrolling leaves out the other dimension**: In the signature above, the only reason the first four parameters can avoid `WSP` and accept a single-layer `Color?` (`CDC`) is that the author cared only about the single boolean `selected` dimension in `WSP` and manually unrolled it into `active*` and `inactive*` flat parameter pairs—duplicating parameters and internal branching for a single dimension while leaving `hovered`, `focused`, `pressed`, and other interaction states completely unsupported; if a property needed to combine 4 dimensions, unrolling flat parameters by state would explode combinatorially. Conversely, wrapping a property in a single layer of `WSP` without unrolling (such as `trackOutlineWidth: WidgetStateProperty<double?>?`) leaves out the brightness and contrast dimensions carried by `CDC`.
2. **If a property uses the nested `WidgetStateProperty<CupertinoDynamicColor>`, it triggers code coloring; disguising that coloring via `implements Color` causes compile-time type erasure**: Supporting full `WSP` state dimensions and `CDC` environment dimensions together without unrolling flat parameters requires the true type `WidgetStateProperty<CupertinoDynamicColor>`. However, that causes the wrapper types to propagate outward from inner evaluation and painting logic, `lerp`/`merge`, and theme fields all the way to public signatures (code coloring). To block that signature contagion, the framework made `CDC` directly implement `Color`, allowing parameters like `trackOutlineColor` to be typed on the surface as `WidgetStateProperty<Color?>` instead of `WSP<CDC>`. The cost is that the type system can no longer distinguish an already-resolved plain `Color` from an unresolved `CDC`—once `WidgetStateProperty<Color?>` resolves to a `Color`, nothing in the static type indicates that it still carries unresolved environment dimensions, so any logic that handles or passes it along as a plain `Color` silently drops its dark-mode and high-contrast dimensions with zero compiler warnings.
3. **Dynamic slots tied to a `Color` subclass cannot generalize to non-color properties, and calling `Color` methods or placing a dynamic color in a container silently degrades it to light mode**: Because the `CDC implements Color` disguise is tied to the `Color` type, adjusting border width (such as `trackOutlineWidth`), font weight, corner radii, or shadows in dark mode or high-contrast mode cannot reuse a "disguised `double` subclass" trick to avoid nested wrappers. And on color properties, before a widget resolves a `CDC`, all of its `Color` member methods and getters (such as `.withValues(alpha: ...)`, `.a`, and `.r`) delegate directly to the default light-mode, normal-contrast slot (`_effectiveColor`). If a developer calls `CupertinoColors.activeOrange.withValues(alpha: 0.48)` before passing it in, puts a dynamic color inside a plain container like `Border` or `BoxDecoration`, or interpolates it with `Color.lerp`, the return value silently degrades to a plain light-mode `Color`, discarding the other 7 environment branches ([#43533](https://github.com/flutter/flutter/issues/43533), [#80860](https://github.com/flutter/flutter/issues/80860)). Even `cupertino_ui`'s own doc comment example for `CupertinoSwitch.trackOutlineColor` (`switch.dart:336`) calls `.withValues(alpha: 0.48)`, which renders the light-mode branch in dark mode.

Ultimately, the struggles in both packages stem from the same root cause: **the current model was built from the outset as a one-dimensional list of static properties, and never treated states and environment dimensions as first-class citizens of the theming system.** As long as the architecture lacks a dedicated structural layer for condition dimensions, every new state or environment dimension can only be patched onto existing properties horizontally (splitting fields) or vertically (wrapping types)—forcing a choice between sacrificing most state dimensions, infecting every signature in the call chain with nested wrapper types like `WidgetStateProperty<CupertinoDynamicColor>`, or disguising wrappers as `Color` subclasses at the cost of compile-time type safety, with every additional dimension multiplying that cost.

## 2.2 Problem 2: Six-Way Semantic Overloading of `null` and Conflicting Imperative Fallbacks in `build`

In existing widgets and theme classes, a single `null` value is overloaded to mean six different things:
1. **Unset at this layer** (fall back vertically to the next theme layer or default value);
2. **Explicitly disable an effect** (for example, `CupertinoButton(pressedOpacity: null)` in older versions meant "do not change opacity when pressed," making it impossible for callers to pass `null` to mean "use the default pressed opacity of 0.4");
3. **Trigger a cross-field fallback** (fall back horizontally, such as reading `foregroundColor` inside `build()` when `iconColor == null`);
4. **Defer to dynamic layout-time calculation** (for example, when a button's `padding == null`, compute padding dynamically during layout from the active `TextScaler`);
5. **"Keep the existing value" in `copyWith`** (making it impossible to reset an already-set field back to `null` via `copyWith`; see [#23036](https://github.com/flutter/flutter/issues/23036));
6. **"Transparent or zero" during `lerp` interpolation** (when Theme A leaves a color unset as `null` and Theme B sets a concrete color, `Color.lerp(null, color, t)` treats `null` as transparent black `0x00000000`; for instance, if `CheckboxThemeData.fillColor` is `null` on one side of a theme transition and non-null on the other, the checkbox fades through full transparency mid-animation).

Overloading `null` with all six meanings—combined with imperative fallback logic hard-coded inside each widget's `build()` method—creates two problems that "coding more carefully" cannot fix:

First, **cross-field fallbacks break during `lerp` interpolation animations**. Consider the rule that a button's icon color follows its foreground color by default. `ButtonStyleButton.build()` implements this fallback as:

```dart
final Color? effectiveIconColor = resolve<Color?>((ButtonStyle? style) => style?.iconColor)
    ?? resolve<Color?>((ButtonStyle? style) => style?.foregroundColor);
```

During static rendering, if a theme leaves `iconColor` unset (`null`), `??` falls back to `foregroundColor` as expected. Now consider what happens when switching themes triggers `AnimatedTheme` (calling `ThemeData.lerp`): suppose the old theme sets only a blue `foregroundColor` (with `iconColor: null`), and the new theme sets both a red `foregroundColor` and a red `iconColor`. At the midpoint of the animation (`t = 0.5`):
- `foregroundColor` interpolates between blue and red, producing an opaque purple-red;
- `iconColor` interpolates from `null` to red, so `Color.lerp(null, red, 0.5)` returns a non-null semi-transparent dark red `rgba(128, 0, 0, 0.5)`;
- When `build()` runs, the left operand of `iconColor ?? foregroundColor` is no longer `null`, so the fallback is skipped entirely. Throughout the transition animation, the button label renders in opaque purple-red while the icon turns semi-transparent and muddy dark red.

Second, **hand-written fallback rules inside `build()` contradict one another without any shared guarantee, creating a minefield for maintainers and a steep cognitive burden for external developers and AI coding tools**. When a property participates in both vertical layer inheritance (`widget -> localTheme -> globalTheme -> default`) and horizontal sibling-field fallback (such as `iconColor -> foregroundColor`), the framework defines no standard order between the two. Across `material_ui`, 37 such cross-field fallbacks are scattered across different widgets' `build()` methods, evolving conflicting precedence rules:
- In `ButtonStyleButton` (such as `FilledButton`), resolution runs **vertically first, then horizontally**: an `iconColor` set in the global theme overrides a `foregroundColor` passed directly at the call site via `FilledButton.styleFrom(foregroundColor: red)`. In `IconButton` right next door, resolution **interleaves by layer**: a call-site `color` (foreground color) overrides an `iconColor` set in the global theme.
- Even within a single widget, layer precedence can vary by field: in icon buttons and `SegmentedButton`, `widget.style` takes precedence over `theme.style` for almost every field, except `iconAlignment`, where the hand-written check accidentally gives `theme` precedence over `widget.style`.
- Some properties enforce hidden mutual-exclusion rules inside `build()`: passing a `TextStyle` with a `color` to `ButtonStyle.textStyle` silently drops that `color`, because the button hard-codes text color to read exclusively from `foregroundColor` ([#81998](https://github.com/flutter/flutter/issues/81998)).
- When maintainers tried to adjust the fallback order for button icon colors in 2024, every `.icon` button in Flutter 3.27 stopped inheriting `foregroundColor`, causing a P1 production regression affecting millions of user apps ([#162839](https://github.com/flutter/flutter/issues/162839)) that had to be hotfixed by hard-coding a 6-step imperative fallback chain inside `build()`.

As long as `null` triggers fallbacks and each widget hand-writes its own precedence rules inside `build()`, interpolation artifacts will persist, and neither human developers nor AI agents will be able to tell which of two related properties wins from the API signature without reading every line of the widget's `build()` method.

## 2.3 Problem 3: Eager Black-Box Derivations (Irreversibly Lost on Override) and the Performance/Size Cost of Centralized Themes

In both token derivation and top-level theme organization, the current model bakes default relationships into constructor-time calculations or private black-box logic, with two direct consequences:

**First, token derivations and specialized calculations are opaque and non-customizable; overriding a property permanently wipes out its built-in dynamic behavior with no way to restore it.**
- **Eager constructor-time evaluation prevents local token overrides from propagating**: `ThemeData` and `ColorScheme` compute derived values eagerly when constructed. For instance, `ThemeData`'s constructor colors `TextTheme` using the `onSurface` value present at construction time, `ColorScheme`'s constructor bakes related colors like `surfaceTint` into concrete `Color` fields, and component defaults stay locked inside 87 private `_XDefaultsM3` classes (a community request to expose default values, [#130135](https://github.com/flutter/flutter/issues/130135) with 73 👍, remains blocked because those internal classes change constantly). If a developer overrides `primary` or `onSurface` in a subtree via `copyWith`, already-constructed dependent fields do not re-derive ([#22913](https://github.com/flutter/flutter/issues/22913)); conversely, developers have no way to declare in their own themes that "property A should dynamically take 12% opacity of token X" or "property A should follow sibling field B."
- **Overriding a single property wipes out implicit dynamic logic with no way to re-attach it**: Many widgets trigger non-standard dynamic behavior inside `build()` by checking whether a property is `null`. The clearest example is **accessible padding scaling** on buttons and `Chip`: by default (when `padding == null`), `ButtonStyleButton` scales horizontal padding across 1x, 2x, and 3x breakpoints during layout based on the active `TextScaler`. Because that scaling logic lives inside the private `padding == null` branch, a developer who simply wants to adjust the base padding (e.g., passing `ButtonStyle(padding: EdgeInsets.symmetric(horizontal: 12))`) makes `padding` non-null and **bypasses the entire accessible padding scaling mechanism**. Worse, because the framework exposes no API to declare or re-attach that scaling policy, overriding `padding` leaves no way to restore the default scaling curve. Similarly, overriding `backgroundColor` in `FilledButtonThemeData` or `IconButtonThemeData` flattens out variant distinctions hidden inside private default classes (such as the difference between `FilledButton` and `FilledButton.tonal`; see [#118063](https://github.com/flutter/flutter/issues/118063) and [#123829](https://github.com/flutter/flutter/issues/123829)) as well as default state derivations for unspecified states, with no way to reconstruct them at the theme layer.

**Second, the monolithic `ThemeData` object causes coarse full-tree rebuilds at runtime and prevents tree-shaking at compile time.**
On the Material side, the global `ThemeData` aggregates 83 fields (including 49 component-specific theme fields and 18 legacy loose color fields). At runtime, because the entire theme hangs off a single `InheritedWidget` without per-component subscriptions ([PR #165289](https://github.com/flutter/flutter/pull/165289)), tweaking any theme field or toggling dark mode triggers a full rebuild of every widget that calls `Theme.of(context)`—in benchmarks, a single 200ms light-to-dark transition on a page with 40 common widgets triggers roughly 46,000 Element rebuilds. At compile time, because `ThemeData` statically references every component's theme class, any app that uses `MaterialApp` forces the compiler to bundle all 50+ component theme classes into the binary, adding roughly 200 KB of non-tree-shakeable code even to a minimal single-line text app. Meanwhile, `cupertino_ui` has not yet built out per-component themes (`CupertinoThemeData` currently has only 8 top-level fields, and widgets like `CupertinoSwitch` and `CupertinoSlider` cannot be styled via themes at all; see [#135110](https://github.com/flutter/flutter/issues/135110)). If `cupertino_ui` copies Material's centralized pattern and piles dozens of component theme fields onto `CupertinoThemeData`, it will repeat the exact same full-tree rebuild overhead and binary size bloat.
