# 2. Problems

---

Engineers who maintain Flutter's first-party widget libraries are familiar with the everyday bugs caused by manually synchronizing 9 places every time a style property is added (across the widget constructor, `XThemeData`, `_XDefaultsM3`, `copyWith`, `merge`, `lerp`, `==`, `hashCode`, and diagnostics)—leading to drifting widget/theme fields, local themes forgetting to extend `InheritedTheme` and dropping across routes, missing fields in hand-written `==`, or branches inside a widget forgetting to call `CupertinoDynamicColor.resolve`.

Yet manual synchronization bugs are only a symptom. Even if code generation were expanded to eliminate all hand-written boilerplate, keeping the underlying `XThemeData` + `WidgetStateProperty` (WSP) + `CupertinoDynamicColor` (CDC) model leaves three structural bottlenecks in multi-dimensional state expression, null fallbacks and interpolation, and black-box derivations and runtime/binary overhead that codegen alone cannot fix.

## 2.1 Multi-dimensional states

At its core, the existing model is a one-dimensional static `property → value` table that never treated states and environment dimensions as first-class citizens. When a property needs to vary by interaction state or environment, the model can only split flat fields horizontally (such as `activeTrackColor` / `inactiveTrackColor`, which explodes combinatorially across multiple dimensions and creates precedence ambiguity alongside `trackColor`) or wrap single properties vertically (`WSP<T>` in Material, `CDC` in Cupertino). This creates distinct dilemmas on each side:

### Material

1. **Repeated conditions across linked properties and broken `resolveWith` equality**: `WSP` hangs off individual properties rather than a style block. Whenever `disabled`, `selected`, or an appearance variant needs to update background, foreground, and border together, the same state branches must be repeated under each property (a scan of 4,200+ production style files found that 82% of button styling relies on `styleFrom` to avoid writing raw `WSP`, while 69% of direct `WSP` usages degenerate into wrapping static constants in `WidgetStatePropertyAll`). As soon as cross-field or opacity derivations are involved (such as pressed overlay color taking 10% opacity of `foregroundColor`), declarative `WSP.fromMap` (under 2% of production usages) cannot express it, forcing a retreat to `resolveWith` closures. In Dart, closure equality (`==`) is always `false`, triggering unnecessary subtree rebuilds and spurious theme interpolation animations whenever an ancestor rebuilds ([#89127](https://github.com/flutter/flutter/issues/89127)).
2. **A fixed global `WidgetState` enum fits neither simple nor complex widgets, blocking custom state combinations**: `WSP` input is locked to the globally shared 8-value `WidgetState` enum. On one hand, simple widgets (like `Switch` or `ProgressIndicator`) use only two or three states, yet the type signature provides no compile-time constraint (`WidgetState.error` or `scrolledUnder` on a `Switch` compiles cleanly but never fires at runtime). On the other hand, component-specific states and variant dimensions—such as `Checkbox`'s tristate (`indeterminate`, currently forced to piggyback on `selected`), button appearance variants (`filled` / `tonal` / `outlined`), or M3E size and shape tiers—cannot fit into a global enum. As a direct consequence, any state combination involving component-specific dimensions (such as customizing a `Checkbox`'s fill color specifically when `indeterminate && disabled`, or overriding a `tonal` button's padding at `large` size in a theme; see [#118063](https://github.com/flutter/flutter/issues/118063), [#123829](https://github.com/flutter/flutter/issues/123829)) cannot be expressed in the existing type system.
3. **Wholesale replacement by local `XTheme` widgets**: Out of 52 `XTheme` widgets, the vast majority of `XTheme.of(context)` implementations return the nearest instance without merging with ancestors. Tweaking a single property in a local scope resets all unspecified properties on that component to `null`, bypassing the global theme and falling straight back to library defaults.

### Cupertino

Cupertino properties frequently need to respond to both interaction states (`WSP`) and 8-slot environment dimensions (`CDC`: brightness, contrast, interface level). Wrapping only one layer either forces manual unrolling of flat state parameters or drops environment dimensions; writing the true nested type `WidgetStateProperty<CupertinoDynamicColor>` infects signatures across the entire call chain (function coloring).

To block signature infection, the framework makes `CDC implements Color` (and similarly `WidgetStateColor`). The price is compile-time type erasure: the compiler cannot distinguish an already-resolved plain `Color` from an unresolved dynamic color. Not only does this trick fail to generalize to non-color properties like border width or font weight, but because `CDC`'s `Color` methods delegate directly to its default light-mode slot (`_effectiveColor`), calling `.withValues(alpha: ...)`, placing a `CDC` inside a `Border`, or passing it through `Color.lerp` before widget resolution silently degrades it into a plain light-mode color, dropping the other 7 environment slots ([#43533](https://github.com/flutter/flutter/issues/43533), [#80860](https://github.com/flutter/flutter/issues/80860)).

## 2.2 `null` and fallbacks

Across existing widgets and theme classes, a single `null` value is overloaded with six distinct meanings: (1) unset at this layer; (2) explicitly disabling an effect (e.g., `pressedOpacity: null`); (3) triggering a horizontal cross-field fallback (e.g., `iconColor ?? foregroundColor`); (4) triggering a layout-time dynamic calculation (e.g., scaling `padding` by `TextScaler` when `padding == null`); (5) "keep existing value" in `copyWith` ([#23036](https://github.com/flutter/flutter/issues/23036)); and (6) transparent black or zero during `lerp` interpolation. This creates two direct problems:

1. **Cross-field fallbacks short-circuit during `lerp` interpolation**: When a theme switch triggers `ThemeData.lerp`, suppose the old theme only sets a blue `foregroundColor` (`iconColor` is `null`) while the new theme sets both `foregroundColor` and `iconColor` to red. At the animation midpoint (`t = 0.5`), `Color.lerp(null, red, 0.5)` treats `null` as transparent black and produces a non-null translucent dark red `rgba(128, 0, 0, 0.5)`. Inside `build()`, because the left operand is no longer `null`, the `iconColor ?? foregroundColor` fallback is skipped, causing the icon to flash dark and translucent throughout the transition.
2. **Hand-written fallback precedences conflict, with long fallback chains that vary by property**: When vertical layer inheritance (`widget -> theme -> default`) interleaves with horizontal sibling-field fallbacks, the 37 hand-written fallbacks across `material_ui` have evolved contradictory rules (for instance, in `FilledButton`, a global theme's `iconColor` overrides a call-site `foregroundColor`, whereas in `IconButton`, a call-site `color` overrides the global theme's `iconColor`; within the same button, `iconAlignment` even reverses layer precedence relative to other fields; and a 2024 attempt to adjust button icon fallback order caused a P1 production regression [#162839](https://github.com/flutter/flutter/issues/162839) that required a 6-step imperative fallback chain in `build()` to patch). Because fallback chains are long and vary from property to property, both human developers and AI tools face a high cognitive burden when reasoning about or maintaining these implicit priorities.

## 2.3 Derivations and centralized themes

1. **Black-box derivations and dynamic behaviors are permanently lost when overridden**: `ThemeData` and `ColorScheme` eagerly compute derived colors into static `Color` values at construction time, while component defaults sit inside 87 private `_XDefaultsM3` classes. Modifying a source token in a subtree via `copyWith` does not recompute already-constructed downstream fields ([#22913](https://github.com/flutter/flutter/issues/22913)). Likewise, dynamic accessibility logic such as scaling button horizontal padding across `TextScaler` stops is hard-coded behind the private `padding == null` branch—passing any custom `padding` bypasses the entire accessibility scaling mechanism, with no entry point to restore it.
2. **Monolithic `ThemeData` blocks tree-shaking and triggers full-tree rebuilds**: `ThemeData` statically aggregates roughly 50 component theme fields on a single `InheritedWidget` ([PR #165289](https://github.com/flutter/flutter/pull/165289)). At runtime, any minor theme tweak or brightness flip rebuilds every widget calling `Theme.of(context)`; at compile time, referencing `MaterialApp` pulls in all 50+ component theme classes and prevents tree-shaking (costing ~200 KB even in a minimal Hello World app).
