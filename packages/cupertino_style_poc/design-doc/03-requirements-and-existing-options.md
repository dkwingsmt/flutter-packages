# 3. Goals & Existing Options

[← Previous: 2. Problems with the Current Model](02-problems.md) | [Table of Contents](00-intro.md) | [Next: 4. Core Design Derivation →](04-core-derivation.md)

---

To address the three structural problems analyzed in Section 2, this section first establishes five design goals for the new model and then uses them as a yardstick to evaluate existing mechanisms in the Dart ecosystem (such as `WidgetStateProperty.fromMap`) and community packages (such as `Mix`, `Remix`, and `Forui`). If adopting an existing Dart implementation as-is could meet our goals (evaluating purely whether its technical architecture fits our requirements, setting aside third-party dependency governance and compliance for now), we could save the cost of building a new system from scratch.

## 3.1 Goals

1. **Compile-time `const` support and structural value equality (`==`)**: Component default rule tables, global themes, and local overrides must all be declarable as compile-time constants (with zero runtime closure allocations) and support `O(1)` identity fast paths along with structural value equality, preventing unnecessary subtree rebuilds and spurious theme interpolation animations caused by style objects always evaluating `==` to `false`.
2. **No property-wrapper coloring, unambiguous `null` semantics, and single-pass multi-dimensional resolution**: Style properties must return to plain value types (`Color`, `double`, `EdgeInsetsGeometry`), where `null` solely means "unset in this rule." Appearance variants (`appearance`), size tiers (`size`), interaction states (`hovered`, `pressed`), semantic states (`selected`, `disabled`), and environment dimensions (`brightness`, `highContrast`, `interfaceLevel`) on the same component must all resolve in a single pass rather than splitting across two separate mechanisms that widgets have to wire together by hand, while remaining backward-compatible when new dimensions are added later.
3. **Unified four-layer customization with incremental merging and intuitive precedence**: Component defaults, global themes, local scopes, and call-site parameters must share a single declarative merging model so that tweaking a single property or specific state in a local layer never wipes out the outer theme wholesale; arbitrary combinations of dimensions must override each other flexibly with intuitive, low-overhead precedence rules.
4. **Explicit, customizable cross-field and cross-token derivations with lazy on-demand evaluation**: Dependencies between fields (such as `iconColor` following `foregroundColor`), global token references, and dynamic calculations (such as scaling padding with text size) must no longer be hard-coded inside opaque `??` chains in `build()` or eagerly baked into concrete values when constructing theme objects. Updating a source field or source token in any subtree must automatically trigger downstream re-derivation, and developers must be able to preserve, restore, or customize these derivations when overriding individual properties.
5. **Minimal runtime and binary-size overhead at scale**: Across dozens of components, hundreds of customizable properties, and more than a dozen state dimensions, dynamic condition matching and derivation evaluation must not compromise frame rates or binary size. At runtime, the system needs multi-stage caching and fine-grained dependency notifications to avoid rebuilding unrelated widgets or re-evaluating rules during local updates and theme animations; at compile time, it must avoid centralized references (supporting tree-shaking) so unused component styles add zero bytes to the final binary.

## 3.2 Evaluating Existing Options

### Option A: Incrementally Patching `XThemeData` + `WidgetStateProperty.fromMap` + `CupertinoDynamicColor`

A natural question is: since the main flaw of `resolveWith` is that closures cannot be compared for equality or decomposed for merging, and Flutter already introduced the Map-based `WidgetStateMapper` (`WidgetStateProperty.fromMap`), could we meet our goals by keeping the existing `XThemeData` architecture, changing local themes to `merge` layer by layer, and adopting `fromMap` across the board?

Patching `XTheme.of(context)` to merge layer by layer does stop local themes from wiping out global configurations, but as long as the underlying architecture wraps states inside individual properties, it still hits four roadblocks:

1. **The `WidgetState` enum cannot represent component-specific or environment dimensions (fails Goal 2)**. `WidgetStateMapper` keys are fixed to `WidgetStatesConstraint`, which can only express the 8 generic interaction states (`hovered`, `pressed`, `selected`, etc.) defined in the `widgets` layer. Component-specific dimensions like `appearance` (such as a button's 5 appearances) and `size`, along with `CupertinoDynamicColor`'s brightness and contrast dimensions, still cannot go into that Map.
2. **Attaching state tables to individual properties duplicates conditions when multiple properties change together**. Even if we extended `fromMap` keys to support conditions across every dimension, keeping the map attached to each individual property means that whenever a single state or variant needs to update multiple properties together—for example, an **interaction state** (`disabled: true` or `selected: true`) updating **3 to 5 color and border properties** (background color, foreground color, icon color, border), or an **appearance and size variant** (`appearance: prominent`, `size: large`) updating **5 to 8 properties** (background color, foreground color, border, corner radius, padding, font size)—developers have to write a separate Map (or `resolveWith` closure) under each property field and repeat the exact same condition structure every time. Our survey of large existing Flutter codebases confirms this: over 80% of button styling code relies on `*.styleFrom` syntactic sugar specifically to avoid writing per-property `WidgetStateProperty` wrappers by hand; as soon as a requirement goes beyond `styleFrom`'s fixed parameter list (such as configuring a `disabled` border, styling a `selected` state, or theming non-button widgets), duplicate state conditions immediately proliferate across multiple properties.
3. **Cross-field and cross-token derivations remain trapped inside a black box (fails Goal 4)**. `fromMap` can only store pre-computed static values; it cannot declare "this field follows another field on the same component" or "this field reads a global token multiplied by an opacity factor." As long as derivation logic relies on `null` fallbacks hard-coded inside `build()`, the precedence conflicts, interpolation short-circuiting, and lost dynamic behavior after overrides described in Sections 2.2 and 2.3 remain unsolvable.
4. **`CupertinoDynamicColor` is tied to `Color` and degrades on method calls (fails Goal 2)**. Non-color properties still cannot adapt to dark mode or high contrast, and calling `.withValues` on a dynamic color before passing it in still strips away its dark-mode branches.

### Option B: Adopting the Community `Mix` Package (and Its `Remix` Component Library)

`Mix` is a widely used styling library in the Dart community (with `Remix` as the component library built on top of it). Inspired by Tailwind and Stitches on the web, it provides generic atomic property builders (such as `BoxStyler` and `TextStyler`), chained variant calls (such as `.onHovered(...)` and `.onDark(...)`), and design token integration via `Prop<T>` and disguised interfaces (such as `ColorRef implements Color`).

`Mix` works very well for developers assembling custom design systems from scratch out of low-level primitives (`Box` / `Flex`), but its core mechanisms differ from the requirements of first-party widget libraries in three ways:

1. **Different target granularity for styles**. `Mix` exposes generic CSS-like atomic layout and paint properties (`BoxStyler`, `FlexStyler`). For first-party widget libraries like `material_ui` and `cupertino_ui`, however, how many internal containers a widget uses or how it structures its `CustomPaint` is a private implementation detail (for instance, upgrading `Switch` to Liquid Glass completely rewrites its internal node tree); first-party widgets must expose stable, component-level semantic properties (like `trackColor` and `thumbColor`), not internal atomic node stylers.
2. **Chained builders cannot be `const`, and disguised tokens suffer from degradation bugs (fails Goals 1 and 2)**. `Mix` relies on chained method calls (`BoxStyler().color(...).onHovered(...)`), which cannot be compile-time `const` expressions in Dart. In addition, to pass tokens into ordinary `Color` or `double` parameters, `Mix` uses `ColorRef implements Color` (which throws via `noSuchMethod` if any property is accessed outside a widget) and negative hash values as sentinel `double` tokens—meaning if a developer accidentally performs arithmetic on a spacing token, it silently produces a negative dimension. This is the exact same class of hazard as the disguised wrapper types analyzed in Section 2.1.
3. **Fixed dimension tiers and composite fragment matching struggle to balance full flexibility with low cognitive load (fails Goal 3)**. To preserve high-priority states by default, `Mix` hard-codes variants into three priority tiers: `base properties < environment variants (e.g., onDark) < interaction state variants (e.g., onHovered)`. While this avoids ordering issues in simple cases, developers have to memorize the tier hierarchy up front; and whenever nested combinations or real-world overrides disagree with the preset tiers (for example, overriding `.onHovered(...)` inside `.onDark(...)`, or layering `focused` on top of `hovered`), unexpected priority inversions easily occur. Meanwhile, its component library `Remix` merges default styles by composite state fragments (such as `onSelected & onDisabled`), forcing external callers to inspect the defaults and write out the exact same composite condition just to replace that fragment, raising the learning curve for local tweaks.

### Option C: Adopting the Community `Forui` Library

`Forui` is another well-crafted community component library. It aligns with our direction in giving each component a strongly typed Style class and using code generation to cut down boilerplate, but its state container `FVariants<K, E, V, D>` and theme architecture diverge from our first-party goals in three areas:

1. **Tokens are eagerly evaluated into static constants at construction time, without symbolic lazy derivations or sibling field tracking (fails Goal 4)**. `Forui` constructs component default styles via factory methods (such as `FButtonStyle.inherit(colors: ..., typography: ...)`) that immediately read concrete `Color` values from `FColors` at the moment `FThemeData` is constructed and store them inside each component's style fields; the resulting style objects hold only baked-in `Color` instances and retain no symbolic record of which token a value came from or which sibling field it follows. This creates two problems: first, **you cannot locally override tokens while preserving outer component customizations**—if a subtree calls `theme.copyWith(colors: newColors)` to swap out color tokens, the 50 component style objects already sitting inside `theme` still hold static `Color` values computed from the old `FColors`, so rebuilt widgets continue rendering the old colors; conversely, calling `.inherit()` again with `newColors` to regenerate `FThemeData` wipes out any component-level style customizations from the outer theme. Second, **there is no cross-field tracking**—for example, a button's text color (`contentStyle`) and icon color (`iconContentStyle`) simply receive the same initial color value when `.inherit()` runs, with no derivation link between them; if a developer changes only the button's text foreground color, the icon color does not follow automatically and must be updated by hand as well.
2. **Tiered dimensions plus specificity sorting adds cognitive overhead and restricts reverse overrides (fails Goal 3)**. To make override outcomes independent of rule order, `Forui` sorts variants first by three dimension tiers (`platform < interaction < semantic`) and then by operand count and lexicographical order within the same tier. While this design has clear engineering rationale, it requires developers to learn and mentally simulate the tiering and specificity math; furthermore, when an app needs a lower-tier dimension (such as the platform dimension `android`) to override a higher-tier dimension (such as the interaction dimension `touch`), writing `android` alone loses, forcing the documentation to instruct developers to write `touch & android` just to boost its tier.
3. **Each property wraps its own `FVariants`, and the top-level `FThemeData` remains centralized (fails Goals 2 and 5)**. Much like `fromMap`, `Forui` wraps every state-dependent property in its own `FVariants` instance, requiring duplicate conditions whenever multiple properties change together under the same state; meanwhile, the top-level `FThemeData` still directly holds fields for all 50 component styles and initializes every one of them eagerly on construction, preventing fine-grained per-component subscriptions and tree-shaking of unused components.

In summary, whether we incrementally patch `XThemeData` + `WidgetStateProperty.fromMap` or adopt existing community implementations like `Mix` or `Forui`, their underlying data structures—per-property state wrappers, eager construction-time evaluation, non-`const` chained builders, or centralized monolithic theme objects—prevent them from satisfying all five design goals in Section 3.1 at once. We therefore cannot reuse an existing implementation off the shelf and need to design and build a dedicated styling and theming foundation for `material_ui` and `cupertino_ui`.
