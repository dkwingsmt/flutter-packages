## 0. Introduction & Overview

### 0.1 Reading Guide & Prototype Repository

Before reading this full design document, we recommend reading the 10-minute [Quick Version (`quick-version.md`)](../quick-version.md). The quick version uses brief code comparisons to explain the structural flaws of the current theming model, the core idea of flipping from "properties on the outside, states on the inside" to "states on the outside, properties on the inside," and why we want to land this first during the Liquid Glass phase of `cupertino_ui`. Building that high-level mental model first will make the derivations and edge-case discussions in this document much easier to follow.

The companion prototype repository in the parent directory (see `README.md` and `example/` in the repository root) implements the rule engine, theme distribution, per-component channel notifications, and cross-route rule capture described here, along with `Button` and `Switch` components built on the new model (backed by pixel-for-pixel regression tests across 448 default appearance cases and 304 flat-parameter cases). You can cross-reference the implementation and tests in the repository as you read each chapter.

### 0.2 Core Design Features & Validation Status

This proposal unifies component defaults, global themes, local scope overrides, and call-site parameters under a single styling model based on pure-data rules. Below is a summary of the core design across each engineering dimension and its current validation status:

**Ergonomics at everyday call sites.** Widget constructors keep the flat parameters developers already know (such as `Button(color: CupertinoColors.systemRed)`). From the rule regions automatically partitioned by the code generator, component maintainers hand-pick the most common properties and state regions to expose as flat parameters, mapping them to rules internally via the corresponding region constructors so they never accidentally clobber dedicated states like `disabled`.

**Preventing unintended overrides and enabling autocomplete for per-state tweaks.** In a purely sequential override model, writing broad conditions by hand can easily clobber narrower state branches in the default rule table (such as changing the enabled state and accidentally overwriting the disabled state). To prevent this, the code generator statically analyzes each component's default rule table, automatically partitions state intervals per property, and generates named region constructors (such as `ButtonRule.backgroundColor(tintedEnabled: ...)`). Combined with Dart's dot shorthands, everyday rule authoring rarely requires spelling out verbose helper class names (for a detailed analysis of how relying heavily on dot shorthands interacts with IDE autocomplete, the Flutter repository style guide, and internal codebase policies, see [Section 9.5](09-topics-and-tradeoffs.md)).

**Spec coverage and pixel-level parity.** We rewrote the default styles of 17 core component groups in `material_ui` (including the new size and shape variants from Material 3 Expressive) as declarative rules and compared every field across all reachable state combinations and 6 color schemes—2,134,974 comparisons with 0 diffs, in roughly 29% of the lines of code of the original `_XDefaultsM3` implementations (1,017 lines vs. 3,529 lines). In the `cupertino_ui` prototype, `Button` and `Switch` match the original widgets pixel for pixel across all appearances, states, and 8 environment combinations, and `CupertinoDynamicColor` automatically expands into environment rules when building the rule chain, eliminating bugs caused by widgets forgetting to call dynamic color resolution methods internally.

**Runtime performance and caching.** All rules, conditions, style containers, and declarative derivations are immutable pure-data objects that support `const` construction and structural value equality, avoiding unnecessary subtree rebuilds caused by `WidgetStateProperty.resolveWith` closures failing equality checks. The evaluation engine uses two-stage caching (symbolic resolution cache + token-bound cache): in a 60-frame theme interpolation benchmark (JIT mode) across 17 Material 3 component groups, the symbolic resolution cache hits 100% on frames 2 through 60, cutting per-frame evaluation time to roughly one-third of rebuilding rules every frame (~205µs vs. 607µs). Local override nodes notify dependents via per-component channels built on `InheritedModel`, so updating button rules does not rebuild switch widgets in the same subtree.

**Binary size and tree-shaking.** The architecture prohibits any central registry or monolithic theme object that references every component type; a component's default rules are referenced only by the component itself, allowing the compiler to tree-shake unused components and their rule classes. Note: comprehensive multi-component tree-shaking benchmarks will be established as more components land; our targeted binary size measurements so far show that unused region constructors add 0 bytes across AOT, dart2js, and wasm, while enabling all of them costs roughly 21 bytes per region on average (AOT), and generated per-component source classes and appearance subclasses cost roughly 61–80 bytes each when actively referenced.

**Code generation and a single source of truth.** Component authors maintain a single declarative definition (the field list and default rule table), while the code generator emits the style class, rule class, region constructors, and interpolation methods directly into source control—eliminating the need to manually update 9 places every time a style property is added. Downstream app developers do not need to run any build-time code generation tools.

**Debugging provenance, static checks, and testability.** The engine provides a `debugSources` diagnostic API that reports, field by field, which layer, rule, dynamic color environment slot, or derivation chain produced the final resolved value; catches type mismatches, circular derivations, and missing token groups at compile time and chain-construction time; and exposes a static `X.resolveStyle(context, ...)` method so unit tests can directly assert resolved styles under any state combination.

**Legacy migration and compatibility.** `cupertino_ui` adopts the new model directly during the rewrite window for new Liquid Glass components. `material_ui` keeps the existing `style:` parameter in place (marked `@Deprecated`) and wraps legacy `ThemeData` fields and `WidgetStateProperty.resolveWith` closures into compatibility rules that evaluate lazily on demand, ensuring a smooth transition for existing app code and third-party packages.

The first half of this document covers the problem space and core design: [Section 1 (Context & Scope)](01-context-and-goals.md) explains why we are doing this now and defines the project's scope and non-goals; [Section 2 (Problems with the Current Model)](02-problems.md) and [Section 3 (Goals & Existing Options)](03-requirements-and-existing-options.md) analyze three structural bottlenecks in the current mechanisms, distill five design goals for the new model, and explain why patching the old architecture or adopting community packages like `Mix` or `Forui` as-is cannot meet those goals; [Section 4 (Core Design Derivation)](04-core-derivation.md) derives the core design in six steps, and [Section 5 (End-to-End Code Walkthrough)](05-walkthrough.md) compares old and new code across five scenarios. If you want to get a feel for the new API as quickly as possible, you can jump straight to Sections 4 and 5 after reading this introduction.

The second half dives into underlying mechanisms and the rollout plan: [Section 6 (Detailed Mechanisms & Code Generation)](06-design-details-and-codegen.md) details the partitioning algorithm for rule regions (6.1), the derivation and token system along with escape hatches (`.computed`, virtual fields, `paddingScaler`) (6.2), partial overrides for composite values and the three-tier value model (6.3), and code generation for shared rules across multiple widgets (6.4); [Section 7 (Engineering Validation)](07-engineering-validation.md) presents benchmarks for two-stage caching, binary size and tree-shaking constraints, debugging provenance, and testing APIs; [Section 8 (Migration & Rollout Plan)](08-migration-plan.md) outlines landing first in `cupertino_ui` and bridging legacy code in `material_ui`; and [Section 9 (Cross-Platform Comparison & Deep Dives)](09-topics-and-tradeoffs.md) discusses cross-platform comparisons, interpolation boundaries during environment switches, implications for AI-assisted coding, and remaining edge cases.
