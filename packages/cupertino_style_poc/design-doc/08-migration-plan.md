# 8. Migration and Evolution Plan

[← Previous: 7. Engineering Validation: Performance, Bundle Size, Observability, and Testing](07-engineering-validation.md) | [Back to Table of Contents](00-intro.md) | [Next: 9. Horizontal Comparisons and Special Topics →](09-topics-and-tradeoffs.md)

---

Because `cupertino_ui` and `material_ui` are at different stages of evolution, the rollout follows a **two-phase strategy**: first, land the new system directly in `cupertino_ui`'s next-generation Liquid Glass components—which carry no legacy component theme baggage—to validate the code generation toolchain and runtime mechanisms end-to-end; next, during `material_ui`'s major version evolution, preserve legacy parameters in place and add a compatibility rule (`legacy rule`) bridging layer for a smooth migration.

---

## 8.1 Phase 1: Landing First in `cupertino_ui` (Liquid Glass)

`cupertino_ui` is currently in a rewrite window to introduce the iOS 26 Liquid Glass component suite. Per the established decision (`lg.export-alongside-legacy`), next-generation components drop the `Cupertino` prefix (e.g., `Button`, `Switch`, `Slider`) and are exported alongside legacy `CupertinoButton` and `CupertinoSwitch`. After a transition period, the legacy components will be deprecated and removed without backfilling component-level themes for them.

Therefore, next-generation Liquid Glass components can adopt the new model directly:
1. **End-to-end pixel-level validation completed in the prototype**: The prototype repository implements the rule engine, `StyleTheme`, `StyleScope`, the code generator, and the unprefixed `Button` and `Switch` (using the existing Cupertino visual spec as a baseline, passing pixel-by-pixel comparisons across **448 default appearance test cases** and **304 flat parameter test cases** spanning all appearances, sizes, states, and 8 environment combinations; the only difference in default appearance is fixing a bug where the original focus ring failed to resolve dynamic colors).
2. **New components built directly on the generated model**: When authors write new Liquid Glass components, a single source of truth generates `XStyle`, `XRule`, `XWhen`, and region constructors; widget constructors retain flat parameters and `rules:`, and **new parameters do not accept `WidgetStateProperty`**; `CupertinoDynamicColor` automatically decomposes into environment sub-rules during rule chain construction.

## 8.2 Phase 2: Incremental Migration and Compatibility Bridging in `material_ui`

`material_ui` has a large set of existing components, 52 `XThemeData` sub-themes, and widespread `Theme.of(context)` calls across application code and third-party packages. Migrating without breaking existing apps requires addressing four questions.

### Question 1: Which widgets share a single set of styles and rules, and how to avoid colliding with `ButtonStyle`?

When auditing existing `material_ui` components, it is important to distinguish two fundamentally different kinds of "sharing":
- **Sharing a property bag across different component kinds (unsupported)**: In the legacy system, `ElevatedButton`, `IconButton`, and `SegmentedButton` share the same `ButtonStyle` class. However, these components differ in internal structure, field sets, and state dimensions (for example, `SegmentedButton` has a `selected` state and multi-segment borders that standard buttons lack; `IconButton` has no text style yet supports filled variants). Sharing a single property bag forces each component to expose many fields that do not apply to it. The new model does not support sharing across different component kinds.
- **Sharing rule types across multiple widgets representing different visual hierarchies of the same component (supported)**: When multiple widgets are essentially the same component differing only in visual hierarchy (`appearance`), their existing widget classes and public APIs stay intact while sharing a single set of style and rule types parameterized by an `appearance` dimension in the styling layer. Each widget passes its corresponding `appearance` dimension when resolving styles.

To decide whether several widgets should share a rule set in the styling layer, **rather than relying on whether they shared a theme channel in legacy `ThemeData`, the design spec is evaluated against three criteria**:
1. **Structural consistency**: Their field sets and supported interactive/semantic state dimensions are substantially identical;
2. **High degree of shared defaults**: Many default rules are identical across variants (if variants share almost no default values, merging them yields no benefit beyond adding an extra `appearance` condition);
3. **Common customizations target shared fields**: Properties that theme authors frequently customize (such as uniformly changing border radius `shape`, font `textStyle`, `minimumSize`, or `padding`) live on shared fields, allowing a single rule without an `appearance` constraint to modify all variants at once.

Evaluating `material_ui`'s button family against these three criteria gives the following breakdown:
- **Five common buttons (`ElevatedButton`, `FilledButton`, `FilledButton.tonal`, `OutlinedButton`, `TextButton`) share the `CommonButton` rule type in the styling layer** (while keeping their widget classes unchanged): Checking the M3 default token tables confirms that these five buttons have identical field sets, with roughly **11 fields** identical across all five appearances (`shape`, `textStyle`, `minimumSize`, `maximumSize`, `iconSize`, `mouseCursor`, `visualDensity`, `tapTargetSize`, `splashFactory`, `surfaceTintColor`, plus disabled foreground and icon colors); `padding` uses the same text-scaling strategy (only `TextButton` has a base horizontal padding of 12, while the rest use 24); differences are confined to properties directly tied to fill hierarchy: `backgroundColor`, `foregroundColor`, `elevation` / `shadowColor`, and `side`. The M3 specification itself groups these five variants under a single component called "Common buttons". Audit data from 17 button theme families across a large codebase corroborates this: `shape` is identical in 8/17 families (plus 2 more where only `TextButton` differs), `textStyle` is identical in 6/6, `padding` is identical in 5/8 (`TextButton` excepted), and `minimumSize` is identical in 4/6; colors differ in 14/16, `side` is only set on `OutlinedButton`, and 6/16 families had to copy-paste identical literal values into every individual button theme just to stay consistent (which collapses into a single rule once merged into `CommonButtonRule`).
  To avoid colliding with Material's existing `ButtonStyle` class and `MaterialButton` widget, this shared type adopts the M3 specification's terminology and is named **`CommonButton`** (generating `CommonButtonStyle`, `CommonButtonRule`, and `CommonButtonWhen`; note that `CommonButton` serves strictly as a prefix for style and rule types without introducing a `CommonButton` widget). At the same time, as described in Section 6.4, the code generator emits appearance-scoped subclasses (`ElevatedButtonRule`, `FilledButtonRule`, `FilledTonalButtonRule`, `OutlinedButtonRule`, `TextButtonRule`).
  Note: Because the existing widget class structure stays unchanged, dynamically switching between `FilledButton` and `OutlinedButton` still requires swapping widget classes (this does not solve subtree `State` preservation when switching across classes); the primary benefit of sharing lies in theme configuration (enabling authors to modify all common buttons uniformly or customize `FilledButton.tonal` individually). An app that only uses `TextButton` will also bundle the default rule data for the other four common button appearances; prototype measurements show that default rule data for a single component is roughly 1–2 KB.
- **Other component families**: The four variants of `IconButton` (standard / filled / tonal / outlined) are structurally identical and share an `IconButton` rule set with an `appearance` dimension; `IconButton`, `SegmentedButton`, and common buttons remain separate components because they include the `selected` state and have different fields. For the `Dialog` family, auditing 6 dialog theme families revealed minimal sharing across `shape` (identical in only 1/6), `elevation` (1/6), and `shadowColor` (3/6), so **the `Dialog` family remains separate and unmerged**; whether `Chip` variants should share a rule type will be determined in a subsequent audit.

### Question 2: How to handle the existing `style: ButtonStyle?` parameter on widget constructors?

**Keep it in place and mark it `@Deprecated`, requiring zero changes to existing call sites.**

In the new design, component constructors accept only curated **flat parameters** and a **`rules:`** rule list, **leaving the `style:` parameter name unused** (the large-codebase audit shows that 82% of button styles are written at call sites, and 94% of those involve no state branching—primarily setting `padding`, background color, foreground color, and `shape`, which map directly to flat parameters). Consequently, the existing `ButtonStyle? style` parameter on `ElevatedButton`, `FilledButton`, and other components can remain in place and be marked `@Deprecated`. When legacy code passes `style: ElevatedButton.styleFrom(...)` or `style: ButtonStyle(...)`, the component internally converts the non-`null` fields of the legacy `ButtonStyle` into instance rules placed before flat parameters and `rules:` (already validated via the legacy `WidgetStateProperty` parameters on `Switch` in the prototype).

Legacy theme channels use the exact same bridging mechanism: `ThemeData(outlinedButtonTheme: OutlinedButtonThemeData(style: ButtonStyle(...)))` bridges internally into a list of `OutlinedButtonRule`s. Note that when migrating component default rule tables, `.fromField(.foregroundColor)` must be used to preserve the implicit derivation relationships where legacy `styleFrom(foregroundColor:)` drives `overlayColor` (0.1 pressed, 0.08 hovered, 0.1 focused) and `iconColor` (in the audit sample, roughly 15/61 call sites rely on this implicit tracking without explicitly setting splash or icon colors). Likewise, when legacy code passes a non-null `padding`, the bridging layer appends `paddingScaler: .identity()` (see Section 6.2) to preserve existing Material behavior where custom `padding` no longer scales with text size.

### Question 3: How to bridge existing `ThemeData`, `XThemeData`, and `WSP.resolveWith` closures?

During the migration transition, existing apps will continue to use `ThemeData(elevatedButtonTheme: ..., colorScheme: ...)` or pass `WidgetStateProperty` to legacy parameters. The bridging layer handles legacy `WidgetStateProperty<T>` instances in two ways:

1. **For `WidgetStatePropertyAll<T>` and `WidgetStateMapper<T>` (`fromMap`)**:
   Convert them into standard rules and insert them at the corresponding position in the rule chain (the theme layer or the call-site flat parameter layer). Note: Because `WidgetStateMapper` uses `WidgetStatesConstraint` keys (whose combinator subclasses are framework-private and allow custom `isSatisfiedBy` implementations), the bridge evaluates the mapper against the component's state combinations and merges identical outputs to produce standard rules; because `fromMap` supports value equality and `const`, the expanded rules can be cached across rebuilds.
2. **For `WidgetStateProperty.resolveWith` closures—wrap them as compatibility rules (`legacy rule`) evaluated lazily on demand**:
   The bridge wraps the closure as-is into a field-specific **compatibility rule** (named `LegacySource` in the prototype to distinguish it from the `.opaque` color transform) and places it in situ at the corresponding layer of the rule chain (closures from `ElevatedButtonThemeData` sit in the theme layer; closures from legacy `widget.style` sit in the call-site layer).
   If and only if the engine resolves that field for a specific state combination and scans backward to reach this compatibility rule, it converts the current state combination into a `Set<WidgetState>` and invokes the closure once (at most 1–2 calls per component `build`):
   - If the closure returns a **non-`null` value**, that value wins immediately and backward scanning stops;
   - If the closure returns **`null`**, indicating that the closure does not specify a value for the current state, the engine continues scanning earlier rules in the chain (outer themes or the library default rule table).

This "lazy on-demand evaluation, continuing backward on `null`" mechanism matches the exact semantics of `widget.resolve(s) ?? theme.resolve(s) ?? defaults.resolve(s)` in legacy `ButtonStyleButton`. Between rebuilds, evaluated state combinations are cached and reused; on each rebuild, they are re-evaluated. Compatibility rules use object identity for equality and do not participate in static shadowing checks or region derivation.

An audit of **122 `resolveWith` closures** sampled from a large codebase validates this model's assumptions: **34%** of the closures depend solely on the passed `states` and return constants, **66%** depend only on external values already fixed during `build` (such as local variables or theme colors), and **fewer than 1%** read mutable external state (such as mutable `State` fields). This confirms that the rule model design (not binding directly to mutable external fields, instead having the call site read external state changes and override via rules or flat parameters) aligns with over 99% of real-world code, and guarantees that caching results per state between rebuilds is safe for existing closures.

**Alternative Comparison: Why not use "Truth-Table Sampling" to convert closures into standard rules?**

Given that over 99% of `resolveWith` closures act as pure functions from a finite `Set<WidgetState>` to a property value within a single `build`, a theoretically appealing bridging approach is **truth-table sampling**: since a component's interactive and semantic state dimensions are finite (e.g., $k$ boolean dimensions such as `disabled`, `hovered`, `focused`, `pressed`, and `selected`, typically yielding 32–64 reachable state combinations after excluding impossible combinations), the bridge could iterate through all 32–64 state combinations during rule chain construction, call `property.resolve(states)` once for each to sample the entire truth table, and merge states with identical return values into equivalent declarative `XRule(XWhen(...))` rules (using the same expansion as `fromMap` above, while omitting rules for states that return `null` so they naturally fall through to earlier rules).

This sampling approach offers two distinct benefits:
1. **Turning black-box closures into transparent declarative rules**: Once sampled and expanded, an otherwise opaque `resolveWith` closure can participate fully in `debugSources` provenance tracking and static shadowing checks just like a native `XRule` (allowing the engine to see exactly what values the closure returns under which states and which default rules it shadows);
2. **Restoring value equality (`==`)**: Even if upstream code passes a newly allocated anonymous closure instance on every `build`, as long as the sampled rule table remains unchanged, the expanded rule list can detect via value equality (`==`) that the style has not actually changed.

Nevertheless, weighing the trade-offs favors **lazily evaluated compatibility rules** at runtime over truth-table sampling:
- **Sampling overhead on rebuilds threatens release performance**: A compatibility rule only invokes the closure for the 1–2 states the component actually occupies during `build`. By contrast, whenever a rebuild creates a new closure, truth-table sampling must eagerly invoke the closure across all 32–64 state combinations and run boolean cube minimization.
- **The benefits of sampling rarely materialize in release builds**: "Supporting value equality after expansion to avoid rebuilds" only matters when `ThemeData` rebuilds and creates new closure instances—yet in existing Flutter, rebuilding `ThemeData` already notifies dependents to rebuild anyway; meanwhile, a closure passed at a component call site only affects that single component instance, where calling the compatibility rule once on demand and reusing caches for everything else is sufficient. As for static shadowing checks and `debugSources` provenance, their value lies primarily in debug development workflows (if needed in the future, debug diagnostic tools can perform on-demand truth-table sampling of legacy theme closures without imposing per-frame sampling costs on release builds).

Two additional runtime characteristics of compatibility rules are worth noting:
- **Fields containing compatibility rules re-evaluate on every `build`**: For the fewer than 1% of closures that capture mutable external fields, their values update as expected on the next component `build`, matching the invocation timing and cost of the existing implementation; once migrated to declarative `XRule`s, they gain `const` canonicalization and cross-frame caching.
- **Natural compatibility with `ThemeData.lerp` transition animations**: In the legacy system, `_LerpProperties<T>` generated by `ButtonStyle.lerp(a, b, t)` is itself a `WidgetStateProperty` that interpolates between both endpoints when `resolve(states)` is called. The bridge treats it as a compatibility rule and invokes it per frame, producing intermediate frame values identical to the existing implementation.

In engineering implementation, the bridging layer must align four details:
1. **Replicate per-field `Set<WidgetState>` filtering passed to closures**: Legacy components do not pass all states to every property (for instance, legacy `Switch` and `Checkbox` filter out `pressed` when resolving track and fill colors, and `Switch` constructs separate selected and unselected state sets to call the closure); the bridge must preserve identical per-field state filtering;
2. **Ensure the component's `XWhen` covers all `WidgetState` dimensions actually passed by the legacy implementation** (such as `error`, `scrolledUnder`, `dragged`, etc.) so corresponding branches inside closures remain reachable;
3. **Handle interleaved fallback logic in specific components**: In components like legacy `IconButton` and `Slider`, certain color fallbacks do not resolve independently per field, but instead interleave based on "which layer provided the property"; the bridge must either align this behavior specifically or document it as a normalizing fix in major-version migration notes;
4. **Compatibility handling for `ColorScheme` constructors**: Calling `ColorScheme(...)` directly to construct a full object continues to fill omitted optional parameters like `surfaceTint` with `primary` for backward compatibility; to locally override only `primary` and let downstream slots automatically re-derive, authors use the generated `ColorScheme` group rule class.

### Question 4: Reverse-compatibility boundaries—how do internal composite pages and third-party packages reading `Theme.of(context)` work?

In an early standalone external prototype package (which defined a parallel `PocButton` class hierarchy), calling built-in framework flows like `showAboutDialog` or `LicensePage` could not pick up `PocButton` themes because those internal pages instantiate native `TextButton` and `Card` widgets. In `material_ui`'s official evolution, however, **`TextButton`, `ElevatedButton`, `Card`, `Dialog`, and other components are modified in place** inside the package so they read `StyleTheme` / `StyleScope` directly (while remaining compatible with legacy `ThemeData`). Consequently, components created by internal composite pages such as `showAboutDialog`, `LicensePage`, and `DatePickerDialog` naturally read `StyleTheme` configurations out of the box.

For application code or unmigrated third-party packages that call `Theme.of(context).colorScheme.primary`, `Theme.of(context).textTheme.bodyMedium`, or `Theme.of(context).cardTheme` directly inside `build()`, the reverse-compatibility boundaries are:
1. **Two-way synchronization for global `ColorScheme` and `TextTheme`**: As described in Step 4 of Section 4, a global token channel manages all slots of `ColorScheme` and `TextTheme` and guarantees non-null resolved values. During the transition period, the top-level `MaterialApp` / `StyleTheme` assembles the current resolved slot values from the global token channel into `ColorScheme` and `TextTheme` instances and injects them synchronously into the fallback `ThemeData`. Any third-party package or legacy code calling `Theme.of(context).colorScheme` or `textTheme` immediately receives the up-to-date color scheme and typography.
2. **Mark legacy `ThemeData.xxxTheme` component sub-theme getters `@Deprecated` (forward bridging only, no reverse evaluation)**:
   If a user configures legacy `ThemeData(cardTheme: ...)`, the forward bridge translates it into `CardRule`s in the rule chain. Conversely, if a user writes `CardRule`s with multi-dimensional conditions or cross-field derivations in the new `StyleTheme`, the system **does not** reverse-evaluate them back into the legacy `Theme.of(context).cardTheme` getter—because a multi-dimensional rule chain and declarative derivations cannot be losslessly collapsed into a static `CardThemeData` object, and stuffing a single state snapshot back into `cardTheme` would mislead callers reading it. Component `xxxTheme` getters on legacy `ThemeData` will be marked `@Deprecated`, guiding external code that needs resolved component styles to call the public `Card.resolveStyle(context, ...)` API instead (see Section 7.6).
