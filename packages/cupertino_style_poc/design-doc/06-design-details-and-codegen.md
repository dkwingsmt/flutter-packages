## 6.1 Detailed Design of Rule Regions and Comparison of Organization Styles

### Region Partitioning, Condition Simplification, and Naming Rules

As described in Step 3 of Section 4, a "rule region" of a field is **the complete set of reachable states where the same library default rule (or a group of default rules sharing the same group tag) wins on that field**. When deriving the region conditions for each field from the default rule table and generating named parameters, the code generator follows four partitioning and naming rules:

1. **Split by individual `appearance` only when the partitioning differs across appearances**:
   When a field has different state partitions (or different winning default rules) under different `appearance` values, the generator first splits by each individual `appearance` and then computes the winning rules within each `appearance`. **It never concatenates multiple `appearance` values (such as `{filled, tinted}`) into a compound parameter name**.
   Because the generator computes regions independently within each appearance, how the author writes the default rule table does not affect the generated parameter names: even if the default table combines three appearances into one shorthand rule (such as `appearance: {.elevated, .outlined, .text}`), the generator will not produce concatenated names like `elevatedOutlinedTextEnabled`. Take `CommonButtonRule`, which is shared by the five standard Material buttons, as an example:
   - `backgroundColor`: Elevated, Filled, and Tonal split into enabled and disabled regions, whereas Outlined and Text remain transparent across all states (only a single region). Because the partitioning differs across appearances, the generator splits by individual appearance and produces `elevatedEnabled`, `elevatedDisabled`, `filledEnabled`, `filledDisabled`, `tonalEnabled`, `tonalDisabled`, `outlinedAnyState`, and `textAnyState`.
   - `foregroundColor`: All five appearances share the exact same state partitioning structure—each takes a distinct value when enabled and `onSurface` × 0.38 when disabled. Therefore, the regions on the superclass do not constrain the appearance, generating `CommonButtonRule.foregroundColor(enabled:, disabled:)` (which applies to all five buttons; to modify only a single appearance, developers can use the appearance-scoped subclasses in Section 6.4, such as `OutlinedButtonRule.foregroundColor(enabled:)`).
   Similarly, `mouseCursor` on Cupertino `Button` has the same partitioning across all appearances, so its parameters are simply `enabled` and `disabled`. If a future design spec update causes one appearance's default partitioning to diverge, the generator can retain the old parameter name marked as `@Deprecated` (automatically expanding it to the newly diverged regions internally) to maintain backward compatibility.
2. **Cupertino `Color` fields fold `brightness` and two other dimensions via `CupertinoDynamicColor` (without splitting them into region names)**:
   This rule applies specifically to `Color` fields in Cupertino. In practice, developers usually redefine the `brightness`, `highContrast`, and `interfaceLevel` dimensions (especially light and dark mode via `brightness`) together with the color itself, and Cupertino already has a well-established convention of using `CupertinoDynamicColor` (which implements `Color` and packs 8 environment slots internally). Therefore, the partitioning algorithm treats the 8 sub-rules unpacked from a single default rule's `CupertinoDynamicColor` as a single region, and region parameter names do not append suffixes like `Light` or `Dark`. Developers can pass a `CupertinoDynamicColor` directly to a single region parameter (e.g., `filledEnabled: CupertinoColors.systemOrange`) to override light/dark mode and high contrast simultaneously. As for Material, a codebase survey shows that developers rarely write light/dark branches directly inside component themes (instead handling them at the token layer or via `isDark ? a : b` scattered in widget code). If `material_ui` wants to offer a built-in light/dark variant syntax similar to `CupertinoDynamicColor` in rules and tokens in the future, the exact form can be decided during the `material_ui` implementation phase. Note, however, that because `CupertinoDynamicColor` subclasses `Color`, forgetting to call `resolveFrom` silently falls back to the light variant; Material would be better served by **a declarative syntax valid only in rule and token source slots (such as `.byBrightness(light:, dark:)`, which similarly unpacks into environment sub-rules during chain construction but avoids the risk of missed resolution because it does not subclass `Color`)**.
3. **Simplify impossible state combinations as don't-care terms**:
   State combinations like `disabled: true` and `pressed: true` (or `hovered: true`) never occur simultaneously during component interaction. Boolean algebra simplification eliminates them as don't-care terms to keep the generated region conditions concise.
4. **Unified, deterministic parameter naming rules**:
   Parameter names follow a fixed concatenation order: `[appearance prefix] + [positive interaction state | idle | enabled | anyState] + [semantic state suffix]`. Here, `enabled` means not disabled regardless of interaction state; `idle` means not disabled and excluding any interaction states specifically handled by that field (for example, if a field defines a dedicated default rule for `pressed`, the remaining non-disabled states are named `idle`). Boolean semantic states (such as `selected`) are appended as suffixes, and the negative suffix (`Unselected`) is spelled out only when the same field also has a positive region.

Note that **the same region name can correspond to different concrete conditions on different fields**. For example, `backgroundColor` on `CommonButton` does not change with `hovered` or `pressed` when enabled (interaction feedback is handled by `overlayColor`), so its `elevatedEnabled` region corresponds to `appearance: {.elevated}, disabled: false`. In contrast, `elevation` has dedicated default values when hovered or pressed, so its enabled states are partitioned into `elevatedIdle` (which includes focused, since the focused elevation matches the resting state), `elevatedHovered`, `elevatedPressed`, and so on. Parameter names directly reflect how that field is actually partitioned in the default rule table.

**Comprehensive statistics on whether there are too many regions or overly long parameter names**:
- **Distribution of region counts**: The vast majority of properties do not vary by state and do not need region constructors at all. Across 17 core component groups and **868 property keys** in Material 3 (including sub-property keys expanded from composite fields), **774 (89%)** have only a single unconstrained region across all states (which the generator skips directly). Only **94 properties actually require region constructors (490 regions in total, averaging about 5.2 regions per property)**, and **99.6%** of those regions correspond to a single `XWhen` cube. In the Cupertino prototype, counting top-level non-composite fields, only 3 of `Button`'s 9 fields have regions (at most 5 regions), and only 4 of `Switch`'s 14 fields have regions (2 regions each). In M3, the field with the most regions within a single `appearance` is `Checkbox.overlayColor` (7 regions); when merging across all `appearance` values onto the superclass, the largest is M3 Expressive's `padding` (16 parameters). Moreover, if a developer is customizing only a single button appearance, using an appearance-scoped subclass from Section 6.4 (such as `OutlinedButtonRule.side(idle:, focused:, disabled:)`) omits the regions of other appearances and strips the appearance prefix.
- **Distribution of parameter name lengths**: Because regions live under field-specific named constructors (so parameter names do not need to repeat the field name as a prefix) and because `idle` / `enabled` eliminate verbose negation chains (like `notHoveredNotPressed`), the generated parameter names average only about **11 characters** (by comparison, concatenating full negation terms without `idle` yields an average length of 24 characters and a maximum of 70 characters). Across the entire dataset, the tiny handful of names exceeding 40 characters all come from stacking multiple specialized non-state prefixes: for example, Material `Switch.thumbRadius` stacks two content boolean dimensions to produce `notHasThumbIconNotHasThumbImageIdleUnselected` (**45 characters**, corresponding to the default small dot radius when there is neither `thumbIcon` nor `thumbImage`, resting and unselected), and `IconButtonM3E` stacks the `outlined` and `Material3Expressive` non-state variant prefixes (such as `outlinedMaterial3ExpressiveFocusedUnselected`, **44 characters**). Beyond these outliers, region parameter names on standard components stay within 1 to 2 words.

### Comparison of Candidate Exposure Forms and Underlying Slot-Expansion Implementation

When deciding how to expose rule regions to developers, several candidate forms were evaluated:

- **Candidate A (Documentation comments only, no generated API)**: Incurs zero binary size overhead, but forces developers to copy `XWhen` conditions by hand with no compile-time feedback when they omit a dimension.
- **Candidate B (Generate a separate constant class per partitioned field, e.g., `ButtonBackgroundColorRegions.tintedEnabled`)**: Defines regions as static constants of type `ButtonWhen` (requiring 94 such constant classes in M3). This approach has two main drawbacks: first, developers must write the property name twice (`ButtonRule(ButtonBackgroundColorRegions.tintedEnabled, style: ButtonStyle(backgroundColor: x))`); second, every constant has the generic type `ButtonWhen`, so developers can pass one field's constant into a rule for a different field. While semantically valid, if two fields happen to share the same partitioning today but diverge in a future release, code that borrows constants across fields will silently break.
- **Candidate C / C' (Generate one region constant class per component, e.g., `ButtonRegions.filledEnabled`)**: Reduces the number of public classes from 94 to 17, but runs into naming collisions: because region names like `idle` are defined relative to a specific field, merging them into a component-level class causes dozens of collisions across the 17 M3 component groups. Generating unique names from the full condition (Candidate C) averages 24 characters and reaches up to 70 characters; appending a property prefix only on collision (Candidate C') averages 20 characters and reaches up to 51 characters, while making names dependent on historical evolution order (if a newly added region collides with an existing constant later, only the new constant can get a prefix).
- **Candidate F (Attach a `StateMap` to each field)**: Because `XWhen` overrides `==`, it cannot serve as a key in a `const Map`. Developers would have to write a list of key-value tuples, effectively reverting to "Direction A" rejected in Step 2 of Section 4.
- **Candidate D (Current choice: generate a `const` named constructor on `XRule` for each partitioned field, e.g., `ButtonRule.backgroundColor(...)`)**:
  Returns a `ButtonRule` directly that slots into `rules: [...]` lists; requires writing the property name only once; and exposes only that field's own region parameters on each constructor, preventing cross-field misuse at compile time.

To prevent Candidate D from bloating binary size, the underlying implementation uses **data-driven slot list expansion (`regionRawRules`)**:
Each region constructor is a `const` constructor containing no branching logic. It simply stores the arguments passed by the user into fixed slots (`_r0`, `_r1`, ...) and references a private `const` region table in the generated file (where each entry records the region name and its corresponding `XWhen` list) along with the target field index. During chain construction, region constructors across all components share **the exact same** generic loop in the engine, which iterates over non-null slots and expands them into engine rules according to the region table. The number of slots matches the field with the most regions in that component (up to 16 parameters for M3E `padding` when split across appearances, adding only about 70 bytes of memory per rule instance).

Binary size measurements across three target platforms—Flutter AOT (arm64 release), Web (dart2js -O2), and Wasm (dart2wasm -O2)—show:
- When an application does not use a given region constructor, the compiler **100% tree-shakes (0 bytes added)** both the constructor and its private region table across all three platforms;
- When an application references all 94 fields and 490 regions in M3, the AOT binary grows by about 10 KB in total, averaging roughly **21 bytes** per region (by comparison, writing equivalent rules by hand with static condition constants takes about 18.6 KB, and generating dedicated expansion functions per field takes about 90 KB).

### Comparison of Three Rule Organization Styles and Region Boundaries

After introducing field-first constructors like `ButtonRule.backgroundColor(...)`, the system has both condition-first `.when(...)` constructors from Step 2 of Section 4 and field-first region constructors from Step 3. To clarify how these two entry points relate, three self-consistent organization styles are compared below:

**Option 1: Condition-first as primary, with region constructors as single-field literal shortcuts (Currently Recommended)**

```dart
...<ButtonRule>[
  .when(disabled: true, style: .values(
    backgroundColor: grey1, foregroundColor: grey2, iconColor: grey2, side: greySide)),
  .when(pressed: true, style: .values(backgroundColor: dark)),
  .backgroundColor(tintedEnabled: brand),
]
```

General rules use condition-first syntax (`.when` / `.always` / `.whenAny`), allowing multiple fields to share a single state condition; `ButtonRule.backgroundColor(...)` is used solely to set literal values for a single field according to the library's default regions (accepting neither custom `XWhen` conditions nor derivation references).
- *Pros*: When a state change updates multiple fields together (a common pattern in both default rule tables and theme customizations), developers write the condition only once; an entire `ButtonStyle` block can be extracted as a named constant for reuse; and evolving toward Option 3 in the future only requires adding optional parameters to `.backgroundColor`, preserving backward compatibility.
- *Cons*: Two entry points exist side by side; when a developer initially uses `.backgroundColor(tintedEnabled: ...)` to tweak a single field and later needs to add a condition outside the default regions (such as restricting it to a specific size), they must rewrite it using `.when(...)` (the doc comments on each region constructor provide the exact equivalent `.when` condition for easy copy-pasting).

**Option 2: Purely field-first organization (remove `.when` / `.always`)**

```dart
...<ButtonRule>[
  .backgroundColor(tintedEnabled: brand, when: [
    (.new(disabled: true), .value(grey1)),
    (.new(pressed: true), .value(dark)),
  ]),
  .foregroundColor(when: [(.new(disabled: true), .value(grey2))]),
  .iconColor(when: [(.new(disabled: true), .value(grey2))]),
  .side(when: [(.new(disabled: true), .value(greySide))]),
]
```

Every rule is written field-first via `ButtonRule.<field>(...)`. In addition to the default region parameters, each constructor accepts a `when: [(.new(...), valueOrSource), ...]` list to support arbitrary conditions and derivations.
- *Pros*: The entire system has a single, unified field-first entry point, grouping all customizations for a given field together in one place.
- *Cons*: When a state or appearance variant updates multiple fields together, developers must repeat the exact same condition under every field; related properties cannot be bundled into a reusable `ButtonStyle` object; and because condition objects override `==` and cannot serve as `const Map` keys, `when:` must be written as a list of tuples, which is less readable than `.when(...)`.

**Option 3: Hybrid coexistence (retain `.when` / `.always` while also adding optional `when:` and derivation support to `ButtonRule.<field>`)**
- *Pros*: Developers can write both single-field and multi-field rules whichever way feels most natural, without switching entry points when adding custom conditions to a default region.
- *Cons*: There are two equivalent ways to "modify a single field under a condition," making it harder for teams to maintain a consistent code style; when mixing the two styles, the relative override order across fields is less obvious than with a single form.

Weighing these trade-offs currently favors **Option 1** (with further statistics planned on the ratio of "single state modifying multiple fields" versus "single field modified by state" across real-world apps and theme libraries). Two clear boundaries also apply to region constructors:
1. **Region constructors accept only concrete literal values (including `CupertinoDynamicColor`), not derivation references**. Derivations (such as `.fromField`) are primarily used in component default rule tables or all-state brand color bindings, which rarely overlap with tweaking literal values by default state regions.
2. **Regions reflect only the component library's compile-time default rule table and are unaware of finer state subdivisions added by upper-level app themes**. For example, suppose a field does not distinguish `pressed` in the library's default table (its default region is a broad `enabled`). If an upper-level app `StyleTheme` adds a press-color rule for that field via `.when(pressed: true, ...)`, and an inner `StyleScope` subsequently calls `XRule.<field>(enabled: blue)`, the inner `enabled` region will override the upper theme's custom `pressed` rule in sequence. If the inner scope needs to preserve custom state branches added by an upper layer, it should use `.when` explicitly.

## 6.2 Detailed Design of Derivations, the Token System, and Leaf-Level Extensions

### Derivation Source Class Hierarchy and Multiplicative `.opacity` Semantics

For the declarative derivations introduced in Step 4 of Section 4, the goal is to guarantee compile-time type safety (for example, disallowing `.opacity` on a `double` field like `borderRadius`) while supporting dot shorthands for all derivation constructors (see [Section 9.5](09-topics-and-tradeoffs.md) for a focused discussion on the dot shorthand assumption). To achieve this, the generator **generates a dedicated source class hierarchy per component** (such as `ButtonSource<T>` and `SwitchSource<T>`, which all inherit from the shared engine base class `DeriveSource`). Generating component-specific `XSource` classes rather than sharing a single generic `Source<T>` across the whole library is necessary because two entry points on the source class bind directly to component-specific static types: first, the static parameter type of `.fromField(ButtonField<T>)` must be fixed to the current component's generic field enum `XField<T>` so the compiler can resolve dot shorthands in `.fromField(.foregroundColor)` and reject cross-component field mix-ups (and because Dart lacks higher-kinded types `F<T>`, a single type parameter cannot constrain field enums across different value types simultaneously); second, the callback parameter `XView` in `.computed(T Function(ButtonView))` must be generated per component because different components have not only different field sets, but also different state and variant dimensions (i.e., the dimensions corresponding to `XWhen`, such as `appearance` and `pressed` on `ButtonView` versus `selected` on `SwitchView`). The derivation source class hierarchy is structured as follows:

- **Standard non-color fields** (such as `borderRadius` and `minimumSize`) have the parameter type **`ButtonSource<T>`** in `.derive(...)`, which provides five constructors: `.value(T)`, `.fromField(ButtonField<T>)`, `.fromToken(CupertinoToken<T>)`, `.fromCustomToken(Token<T>)`, and `.computed(T Function(ButtonView))`. The field enum `ButtonField<T>` is a generic enhanced enum where each enum value carries its own field type, so passing a `Color` field into a `padding` slot or mixing field enums from another component triggers a compile-time error.
- **Color fields** (such as `backgroundColor` and `foregroundColor`) have the subclass parameter type **`ButtonColorSource extends ButtonSource<Color>`** (because Dart constructors are not inherited, the generator replicates the five base constructors on the subclass) and provide two additional color transformation constructors:
  1. **`.opacity(ButtonColorSource source, double opacity)`**: **Multiplies** the alpha channel of the upstream color source by the given factor (i.e., `clamp(source.a * opacity, 0.0, 1.0)`) rather than replacing the alpha value outright. This design uses **multiplicative semantics** because when the upstream color is intentionally semi-transparent (for instance, a caller passes a brand color at 80% opacity), a derived color (such as `.opacity(.fromField(.foregroundColor), 0.5)`) should scale proportionally down to 40% rather than jumping to 50%. This matches the semantics of SwiftUI's `Color.opacity`, Android `ColorStateList`'s `android:alpha`, and CSS `opacity`; for opaque source colors in library default rules, multiplication and replacement produce identical results. The `opacity` parameter must be a non-negative finite number (values greater than 1 are allowed to boost the opacity of a semi-transparent source). Because the first parameter is itself a `ButtonColorSource`, `.opacity` works on fields, tokens, dynamic color literals (`.opacity(.value(CupertinoColors.systemRed), 0.5)` is how you express a semi-transparent dynamic color in a `const` context), and nested sources. Note: when migrating `material_ui`, if existing code sets tokens like `onSurface` to semi-transparent colors, stacking `.opacity(..., 0.38)` for the disabled state will change from alpha replacement to alpha multiplication, which should be noted in the migration guide.
  2. **`.opaque(ButtonColorSource source)`**: Forces alpha to `1.0` while preserving the RGB channels. For example, the original Cupertino `filled` button calls `withOpacity(1.0)` on `primaryColor` to force it opaque; under multiplicative semantics, this becomes `.opaque(.fromToken(.primaryColor))`. It also supports nested composition (such as `.opacity(.opaque(x), 0.5)`).

### Underlying Design of the Token System: Facade Evolution, Eliminating Data Classes, Dual Rule Base Classes, and Engineering Practices

For the global and custom `TokenGroup` mechanisms introduced in Step 4 of Section 4, the underlying API design and trade-offs are as follows:

1. **Why built-in library tokens are not exposed directly as an `enum`, and why `.fromToken` is split from `.fromCustomToken`**:
   - **Non-breaking evolution of the built-in facade**: In Dart, once downstream code uses a public enum in an exhaustive `switch` statement, adding a new enum value in a minor framework release breaks downstream compilation. Therefore, built-in library tokens are exposed as **`static const` constants** on `abstract interface class CupertinoToken<T extends Object> implements Token<T>` (e.g., `CupertinoToken.primaryColor`, backed by a package-private enum under the hood).
   - **Dot shorthand ergonomics**: Because dot shorthands look up static members on the declared static type of a parameter, `.fromToken` declares its parameter type as `CupertinoToken<T>`, allowing built-in library tokens to be written concisely as `.fromToken(.primaryColor)`. Custom application tokens, on the other hand, implement the base interface `Token<T>` (Dart does not allow retrofitting an existing `enum` to implement a new interface, nor can custom enum values become static members on `CupertinoToken`), so developers pass them by their qualified enum name via the dedicated `.fromCustomToken(MyBrand.accent)` constructor (and `s.customToken(MyBrand.accent)` on callback views).
2. **Why whole-group data classes (`MyBrandData` / `groupOf`) and whole-group value rules are omitted**:
   Early iterations considered requiring users to define an additional non-nullable data class `MyBrandData` containing all fields—similar to `ThemeExtension`—alongside an exhaustive `of(MyBrandData)` on the enum, `StyleTheme.groupOf<MyBrandData>`, and a whole-group literal rule `MyBrand.group.set(data)`. After auditing 21 production projects (91 `ThemeExtension` classes with 1,149 fields), this layer was removed entirely:
   - **Real-world presets are essentially rule lists, not pure literal value objects**: In the audit, roughly **60 of the 91** extension classes contained light/dark mode variants (**7** included high-contrast variants), and many extensions contained derived semantics (roughly **49** alias getters, **32** opacity variants, **37** `ColorScheme` references, and **10** fallback getters). Expressing a preset as a static rule list (such as `MyBrandRule.teal`) unifies default values, environmental condition branches (`TokenWhen(brightness: .dark)`), and inter-token derivations (`.setFrom`) within a single list. Conversely, expressing a preset as a data object where every field is required cannot represent derivation relationships at all, and expanding it would overwrite and wipe out any derivation rules placed earlier in the chain.
   - **`CustomPainter` does not need a whole-group data class**: The only plausible use case for reading an entire group at once is passing a bundle of resolved tokens to a `CustomPainter`. Yet across all 21 projects, only **17 files** passed extension values into a `CustomPainter`: **15 of them (88%)** already read individual tokens one by one and passed them as separate fields (with a median of just **2 values**, often accompanied by `/ 2` or opacity adjustments at the call site). The remaining **2 painters (12%)** that accepted an entire `ThemeExtension` object actually read only **7% (4/56)** and **3–6% (1/16)** of its fields, and both had broken `shouldRepaint` implementations (one hardcoded `false`, while the other performed reference equality on an extension object that did not override `==`). When a painter genuinely needs to bundle multiple resolved tokens and get value-based equality in `shouldRepaint` automatically, reading them at the `build` boundary and packing them into a native Dart **Record** solves the problem with zero boilerplate:
     ```dart
     typedef RingColors = ({Color done, Color track});
     final RingColors colors = (done: MyBrand.success.of(context), track: MyBrand.textMuted.of(context));
     final double inset = MyBrand.radius.of(context) / 2; // Perform numeric math right after reading
     // RingPainter.shouldRepaint(RingPainter old) => old.colors != colors || old.progress != progress;
     ```
   - **Perform type conversions at the consumption site or inside `.computed`**: The audit found **14 getters** that existed solely to convert a `double` into `BorderRadius.circular(r)` or `Radius.circular(r)`. Keeping `radius<double>()` as a single primitive numeric token and calling `BorderRadius.circular(MyBrand.radius.of(context))` directly at the widget consumption site (or converting it via `.computed(brandRadius)` in component rules) avoids maintaining two duplicate tokens for the same concept.
3. **`TokenWhen` environmental conditions, dual rule base classes (`TokenValueRule` vs. `TokenSourceRule`), and single-token methods (`.set` / `.setFrom`)**:
   - **How `TokenWhen` is generated and the boundary of environmental dimensions**: Because `material_ui` and `cupertino_ui` do not share engine runtime code (they share only the code generator), each component library first defines its own full set of built-in environmental dimensions (such as `brightness`, `highContrast`, and Cupertino's `styleVariant`). The condition class **`TokenWhen`** for the global token channel uses all built-in environmental dimensions of the current library, whereas each component's `XWhen` includes only the subset of environmental dimensions that the component's default rule table actually distinguishes (the direction is "the library defines the full environmental dimension set `TokenWhen`, and each component's `XWhen` takes a subset," rather than reverse-extracting from components). For app-specific custom environmental dimensions beyond the built-in ones (such as a third OLED pure-black / eye-care theme mode or responsive screen-width breakpoints), the system intentionally omits an extension mechanism for custom `When` dimensions—developers can simply read the current environment or breakpoint when building `StyleTheme` / `StyleScope` and conditionally mount the corresponding rule list, avoiding extra complexity in the engine and cache keys. (Note: in the primary design, the binary enum `brightness` uses a scalar `Brightness?`, i.e., `brightness: .dark`; to reserve room for light/dark mode to expand beyond two enum values in the future, an alternative is to generate it uniformly as a set type `Set<Brightness>?`, i.e., `brightness: {.dark}`.)
   - **Division of labor between `TokenValueRule` and `TokenSourceRule` (corresponding to `.values` and `.derive` in component styles)**: Most custom extensions consist primarily of literal values with only a few derivations. For these, subclassing `TokenValueRule` (overriding `get values`) is recommended, where constructor parameters accept plain value types (`final Color? accent`) without wrapping every value in `.value(...)`, and pairing any occasional derivations with `MyBrand.textMuted.setFrom(...)`. If a group involves extensive inter-token derivations, developers can subclass `TokenSourceRule` (overriding `get sources`), where constructor parameters accept the shared `TokenColorSource?` (supporting `.value`, `.fromToken`, `.fromCustomToken`, `.opacity`, and `.opaque`) or `TokenSource<T>?`, and the base class automatically separates literal values from derivation sources. Meanwhile, the framework's built-in, code-generated `CupertinoTokenRule` extends `TokenSourceRule` and provides both a flat-value primary constructor and a `const CupertinoTokenRule.derive(...)` named constructor (note: if a handwritten class uses Dart's primary constructor syntax `final class const MyBrandRule({...})`, language rules prohibit declaring an additional non-redirecting `.derive` generative constructor, so handwritten rule classes simply pick whichever base class fits their needs).
   - **Why `.set` / `.setFrom` are instance methods on `Token<T>`**: Because generic type parameters in Dart are covariant, `MyBrand<Color>` is also a subtype of `Token<Object>`. Under a static generic function `TokenRule.value<T>(Token<T> token, T value)`, if a user accidentally wrote `TokenRule.value(MyBrand.accent, 3)`, the compiler would upcast `T` to the least upper bound of `Color` and `int`—namely `Object`—and let the bug compile silently. Making `MyBrand.accent.set(T value)` and `.setFrom(DeriveSource<T> source)` instance methods on `Token<T>` locks the target type `T` to `Color` on the receiver, catching mismatched types at compile time.
   - **Non-`const` equality guarantees for `.set`**: Dart does not support `const` method invocations, so `MyBrand.accent.set(x)` is not a compile-time constant. However, `TokenRule` overrides `==` and `hashCode` to compare the expanded `when`, literal map, and derivation map entry by entry, so creating rules inline inside `build` will not trigger unnecessary downstream `InheritedModel` rebuilds. To skip per-`build` list allocations as well and hit the `identical(a, b)` fast path, developers can hoist rule lists containing `.set` / `.setFrom` into top-level or `static final` constants; when `MyBrandRule` is already defined, using `const MyBrandRule(accent: x)` is preferred since it yields a compile-time constant directly and sets multiple tokens in batch under a single `when:`.
4. **Built-in interpolation dispatch table, `lerpObject`, and container boundaries**:
   - **Built-in type interpolation table**: Across the 1,149 extension fields audited, `Color` accounts for **79% (910 fields)**, `double` for **80**, `TextStyle` for **68**, `ShapeBorder` / `BorderRadius` for **11**, and `BoxShadow` for **2**. The engine includes a built-in runtime-type interpolation dispatch table covering `Color`, `double`, `TextStyle`, `EdgeInsetsGeometry`, `BorderRadiusGeometry`, `AlignmentGeometry`, `Size`, `Offset`, `ShapeBorder`, `BorderSide`, `IconThemeData`, `List<BoxShadow>`, and `List<Shadow>`, handling **99% of interpolatable fields** in real-world projects out of the box. Non-interpolatable types (such as the **48 `String` asset paths**, `bool`, `int`, enums, and callbacks in the audit) step discretely at `t = 0.5` by default; nested custom composite classes (such as the **8 semantic color group fields** `SemanticGroup` in the audit) simply pass `lerp: SemanticGroup.lerp` explicitly on the enum value, and fields requiring non-linear interpolation or forced step transitions (by passing the framework-exported `discrete` function) configure `lerp:` the same way.
   - **Using `lerpObject` to avoid contravariant parameter type-erasure errors**: The function type of the `lerp` field is `T? Function(T?, T?, double)?`, placing the type parameter `T` in a contravariant parameter position. Because the engine holds a collection of `Token<Object>` internally, reading `token.lerp` directly from the engine would throw a Dart runtime type cast error. To prevent this, `GroupTokenMixin` provides the wrapper method `lerpObject(Object? a, Object? b, double t)`, which invokes the interpolation function within the scope of the token's concrete type `T`.
   - **Dynamic color boundaries inside custom opaque containers**: When a `CupertinoDynamicColor` is assigned directly to a `Color` token (e.g., `MyBrandRule(accent: CupertinoColors.systemBlue)`), the chain construction phase automatically unpacks it into standard rules matching light/dark mode and high contrast. However, if an unresolved `CupertinoDynamicColor` is buried inside an opaque custom container unknown to the engine (such as `SemanticGroup(bg: CupertinoColors.systemBlue)`), the engine cannot reach inside to unpack it. In debug mode, an assertion catches this immediately and prompts the developer to configure separate light and dark containers via explicit `TokenWhen(brightness: .dark)` rules instead.
5. **Omission semantics and why `…OrNull` is not provided (best practices for test mounting and design-refresh toggles)**:
   - **Rule omission and missing-configuration error boundaries**: In `MyBrandRule`, leaving a constructor parameter as `null` means "this rule does not touch that token; keep using the value from earlier rules in the chain." Every custom `TokenGroup` must be registered in the root `StyleTheme(groups: [...])`. If application code calls `MyBrand.accent.of(context)` when the group has not been registered, or if no rule assigns a final value to `MyBrand.accent` under the current environment (for example, omitting an entry or misspelling a key when writing the `MyBrandRule.values` map by hand), reading the token immediately throws a `RuleError` pinpointing the exact group and token name.
   - **Why `maybeOf` / `…OrNull` is omitted**: Across the 21 projects audited, only **2 projects** defined `…OrNull` helper methods. Inspecting every call site revealed that neither project actually had "optional token" semantics:
     1. **Unit tests or preview harnesses mounting an incomplete theme**: In the first project, the production `MaterialApp` always registered the extension, which was missing only in widget tests or Storybook previews running a bare `ThemeData()`. Introducing `…OrNull` to accommodate unconfigured tests forced **30 production component files (at least 112 read sites)** to carry dead fallback branches (`tokens?.x ?? colorScheme.y`) that never executed in production. In this model, `MyBrand.accent.of(context)` always returns a non-nullable `T`; tests and previews should mount the app's real `StyleTheme` through a shared test helper (and if someone forgets, `RuleError` flags the missing setup immediately instead of silently falling back):
        ```dart
        Future<void> pumpApp(WidgetTester tester, Widget child, {Brightness brightness = Brightness.light}) =>
            tester.pumpWidget(StyleTheme(
              groups: [MyBrand.group],
              rules: appTokenRules,
              child: MediaQuery(data: MediaQueryData(platformBrightness: brightness), child: CupertinoApp(home: child)),
            ));
        ```
     2. **Using extension presence as a feature flag for a design refresh (`v1` vs. `v2`)**: In the second project, **26 production files (roughly 41 call sites)** checked `brandTokensOrNull(context) != null` to branch between legacy base colors and a new brand redesign. Encoding a feature flag as "whether a theme extension is null" scatters version-checking logic across every feature widget. In this model, the redesign flag is read in one place when building `StyleTheme` or a local `StyleScope`. Unmigrated pages simply mount a set of compatibility rules (legacy rules) that derive `MyBrand` tokens from built-in base tokens, allowing all downstream widgets to call `MyBrand.accent.of(context)` unconditionally (and dependent tokens like `textMuted` automatically recompute from the legacy primary text color):
        ```dart
        const legacyRules = [
          MyBrandRule(accent: .fromToken(.primaryColor), textPrimary: .fromToken(.labelColor)),
        ];
        StyleScope(rules: flags.settingsRedesigned ? const [] : legacyRules, child: const SettingsPage());
        ```

### Leaf-Level Extension 1: Per-Field Computed Callback Derivations (`.computed`)

For the small number of complex calculations that `.fromField`, `.fromToken`, and `.opacity` cannot express directly—such as dynamically choosing a light or dark foreground label based on the luminance of the resolved `backgroundColor`, shifting lightness in HSL color space to generate a focus ring color, or converting a `double` corner-radius token into a `BorderRadius`—`ButtonSource<T>` provides a per-field **computed callback derivation `.computed`** (this mechanism is a self-contained leaf-level extension that the rest of the engine does not depend on):

```dart
// Top-level function: its tear-off is a const expression
Color focusRing(ButtonView s) {
  // s is a lazy evaluation view for the same instance and state; returns non-nullable Color thanks to the full-coverage invariant
  final HSLColor hsl = HSLColor.fromColor(s.field(.backgroundColor));
  return hsl.withLightness((hsl.lightness + 0.25).clamp(0.0, 1.0)).toColor();
}

const ButtonRule.always(style: .derive(focusColor: .computed(focusRing)))
```

How `.computed` works and its boundaries:
- **Evaluation semantics**: The callback function `(s) => ...` computes only its target field, and the parameter `s` is a lazy evaluation view of the same component instance under the **current state combination**. Thanks to the full-coverage invariant, calling `s.field(.backgroundColor)`, `s.token(.primaryColor)`, or `s.customToken(MyBrand.accent)` **always returns a non-nullable `T` directly**. If the callback reads back the currently evaluating field along a dependency chain, the evaluation stack catches the re-entrancy at runtime and throws a `RuleError` with the full dependency trace.
- **Caching and performance**: When the computation is defined as a top-level function or static method and passed via tear-off (such as `.computed(focusRing)`), the entire rule remains `const`, hitting both the first-stage symbolic cache (`SymbolicCache`) and the second-stage bound cache (`BoundCache`) normally. Using an inline anonymous closure makes the rule non-`const`, causing the instance rule chain to rebuild on every frame (taking roughly 26µs per frame for a single `Button`, compared to 1.6µs with a tear-off).
- **View implementation and measured binary size**: The callback view `ButtonView` is a component-specific `extension type` that exposes only generic read methods `s.field(.x)` / `s.token(.x)` / `s.customToken(x)` (rather than generating a separate getter per field). In an extreme synthetic benchmark reading all 40 fields across 75 components, generating per-field getters added 832 KB because the AOT compiler stopped inlining, whereas the single generic-method view added only 237 KB (roughly 3.5× smaller); in typical usage reading only a few fields, the two differ by just 1–2 KB. When the engine includes `.computed` support but an app does not use it, the baseline AOT overhead is only about 3.5 KB, and each actual callback usage costs roughly 340 B. To ensure effective tree-shaking, the component library's own flat parameters never create callback rules on the user's behalf; callback rules appear only when the default table genuinely requires complex math (such as an HSL focus ring) or when a developer writes one explicitly.
- **Limitations**: Circular dependencies inside inline closures can only be detected at runtime when evaluating the matching state; `debugSources` can report only "from computed rule #n" without statically listing which upstream fields the closure read internally; and callbacks must remain pure functions (enforced by documentation conventions).

### Leaf-Level Extension 2: Virtual Fields — Sharing Values Across States

Both `.fromField` and `.computed` read other field values resolved under the **exact same state combination** on the component. The engine does not allow querying a field's value from `selected: true` while resolving `selected: false`—allowing arbitrary cross-state reads would break state-independent evaluation, causing cache complexity to grow quadratically with the state space and introducing cross-state circular dependencies.

For the rare design spec requirement that genuinely needs to "share a color across states"—for example, legacy `CupertinoSwitch` requires that when an unselected switch (`selected: false`) receives keyboard focus, its focus ring still uses **the active track color from the selected state (`selected: true`)**—the **virtual fields** pattern solves this cleanly: declare a field in `SwitchStyle`'s generated definition that is not used directly for final painting (such as an `accentColor` that does not partition by `selected` by default, acting as an internal component-scoped token). In the default rule table, both the selected `trackColor` (when `selected: true`) and the focus ring's `focusColor` (when `focused: true`, regardless of selection) derive from that field via `.fromField(.accentColor)`. This keeps every state combination completely independent during evaluation while cleanly sharing the color across states.

### Leaf-Level Extension 3: Text-Scale-Adaptive Padding (The `padding` + `paddingScaler` Dual-Field Pattern)

Under the Material 3 accessibility specification, when the system font scale increases (`TextScaler` > 1.0), buttons and chips must proportionally reduce their horizontal padding following a piecewise linear curve to leave horizontal room for larger text (for example, halving horizontal padding at 2× font scale and reducing it to 1/4 at 3× font scale).

The legacy implementation tied this scaling behavior to `padding == null`: as long as the user did not pass `padding` (leaving it `null`), the widget dynamically shrank the default padding during layout according to the font scale; the moment a user passed any non-null `padding: EdgeInsets.all(16)`, accessibility padding scaling silently stopped working.

To eliminate "relying on `null` to trigger hidden layout logic" and make accessibility padding scaling an independently configurable capability, the design splits it into two orthogonal style fields:
1. **`padding: EdgeInsetsGeometry?`**: The base padding at a text scale factor of `1.0` (populated with concrete `EdgeInsets` constants in the default rule table and non-null after resolution);
2. **`paddingScaler: PaddingScaler?`**: A pure-data policy object describing how layout adjusts the base padding according to the current text scale factor, offering two `const` constructors: `const PaddingScaler.identity()` (no scaling) and `const PaddingScaler.stops({1.0: 1.0, 2.0: 0.5, 3.0: 0.25})` (piecewise linear scaling).

**Why not use a `ScaledPadding extends EdgeInsets` subclass?**
Having `ScaledPadding` subclass `EdgeInsets` to hide the scaling policy inside the padding value suffers from the same pitfalls as disguised types: because `EdgeInsets.==` compares only the four edge offsets, comparing a plain `EdgeInsets` on the left against a `ScaledPadding` with the same base values evaluates to `true`, potentially skipping necessary rebuilds; furthermore, performing standard operations like `+`, `copyWith`, or `resolve` on the object degrades the return value back into a plain `EdgeInsets`, silently dropping the scaling policy. Splitting them into two separate fields keeps the types and equality semantics clean.

During widget layout, the component simply calls `resolved.paddingScaler!.apply(resolved.padding!, textScaler, fontSize)`. Under the new API, if a developer modifies only the base `padding`, the default `paddingScaler` remains intact, preserving accessibility padding reduction at large font sizes; if they explicitly want to disable scaling, they can pass `paddingScaler: const .identity()`. Meanwhile, in the compatibility bridge for the legacy `ButtonStyle(padding: ...)` API (see Section 8.2), whenever the bridge detects a non-null `padding` from the old API, it also emits `paddingScaler: .identity()` to preserve existing behavior for legacy code.

## 6.3 Detailed Design of Partial Overrides for Composite Values (Three-Tier Value Model and `.parts`)

### Conceptual Boundary: Why "Partial Override" Differs from "Derivation" Yet Shares the `.derive(...)` Slot

Regarding **partial overrides for composite values (the three-tier value model: `Mergeable` / `Patchable` / `Atomic`)** introduced in Step 5 of Section 4, an easily conflated conceptual boundary warrants clarification first—**derivation and partial override solve two orthogonal problems**:
- **Derivation (Section 6.2)** answers **"where is a property's value dynamically computed from?"**: it reads **other sibling fields** under the same state (`.fromField`), **global tokens** (`.fromToken` / `.fromCustomToken`), or **computed callbacks** (`.computed`), and never reads the current field's own value from preceding rules;
- **Partial override (this section)** answers **"how to keep the rule model from getting in the way of ergonomic style API design"**: if the rule model cannot update specific sub-properties of a composite value while inheriting the rest from preceding rules, the style API is forced either to abandon composite types and flatten everything into scattered top-level fields (like `sideColor` and `sideWidth`), or to keep composite types at the cost of terrible ergonomics (forcing users to re-specify border width just to change border color, or making it impossible to bind a token to a single sub-property).

Placing `.parts(...)` for `Patchable` types (as well as `.parts(...)` when binding a derivation reference to a sub-property of a `Mergeable` type) inside `style: .derive(...)` is purely **a syntactic slot reuse**: in `style: .values(...)`, each field's static parameter type is the native Flutter value type itself (such as `BorderSide?` or `TextStyle?`). Because every parameter on the native `BorderSide` constructor has a non-null default value, `.values(...)` cannot express "change only the color without touching the width" or pass a derivation source to an individual sub-property. In `style: .derive(...)` (`XStyleSpec`), however, every field's parameter type is already the wrapper class `XSource`. The generator therefore generates dedicated source subclasses for composite fields that support partial overrides (such as `ButtonTextStyleSource` and `ButtonBorderSideSource`) and provides the `.parts(...)` constructor on them:

- **Structure of dedicated composite source subclasses**: In addition to replicating the five base constructors from Section 6.2 (`.value`, `.fromField`, `.fromToken`, `.fromCustomToken`, and `.computed`, which replace the composite field as a whole), they provide **`.parts(...)`**. Each sub-property parameter inside `.parts(...)` is typed to the component's corresponding source class (for example, `color` has type `ButtonColorSource` and `width` has type `ButtonSource<double>`), so individual sub-properties can accept either literal values like `.value(red)` or derivations like `.fromField(.foregroundColor)` and `.opacity(...)`.
- **Stacking order of whole-value replacement and partial patching**: Setting a field as a whole (e.g., `textStyle: .fromToken(...)`) and patching its sub-properties (e.g., `textStyle: .parts(color: .fromField(.foregroundColor))`) share the same field parameter slot; to "set the base value first and tweak a sub-property second," developers simply write two rules in sequence without needing a separate `base:` parameter. Note that referencing a composite token as a whole via `.fromToken` / `.fromCustomToken` (such as a `TextStyle` token) always resolves to a complete value containing all sub-properties; therefore, placing a whole-token reference **after** a `.parts(...)` partial patch rule will overwrite the earlier partial patch.

### Four Technical Boundaries of the Three-Tier Value Model and Trade-Offs for `EdgeInsetsGeometry`

Underneath the three-tier value model (`Mergeable` / `Patchable` / `Atomic`) and `.parts(...)` projection patching lie four key technical boundaries and design trade-offs:

1. **Why nullable mirror classes (such as `BorderSideStyle`) were rejected for types like `BorderSide`**:
   Early in the design, adding a superclass or mirror class `BorderSideStyle` with all-nullable fields for `BorderSide` was evaluated so that it could behave as a `Mergeable` type just like `TextStyle` (merging directly inside `.values(side: BorderSideStyle(color: red))`). However, this approach had clear drawbacks: first, it required intrusively modifying the public class hierarchy in `flutter/painting`; second, `BorderSide(...)` and `BorderSideStyle(...)` differ by only a suffix yet have completely opposite merging semantics (omitting `width` in the former resets it to `1.0`, whereas omitting it in the latter inherits from preceding rules), making mistakes all too easy; third, it is impossible to create a mirror class for an abstract base class like `EdgeInsetsGeometry`. Keeping native Flutter value types untouched and providing `Patchable` updates uniformly through `.parts(...)` is far less intrusive and much more consistent.
2. **Rule idempotency and why `.inherited()` and delta operators were rejected**:
   Applying the same rule twice in a row on a chain must produce the exact same result as applying it once ($f(f(v)) = f(v)$). Consequently, any operation that reads the preceding rule's result for the same field must be strictly a **projection replacement (`.parts`)**. `.inherited((prev) => ...)` callbacks and `prev.add(delta)` incremental operators were explicitly rejected: allowing arbitrary reads or accumulations on previous values not only makes it trivial for users to write non-idempotent rules (which the engine cannot detect statically), but also forces caching to degrade from "caching by the final winning rule" to "caching at every intermediate position along the entire chain," while exploding the complexity of default-table exhaustiveness checks and multi-stage provenance tracking.
3. **Specific constraints on `Mergeable` and `Patchable`**:
   - **`Mergeable` sub-properties cannot be "unset (reset back to null)," and rule merging ignores `TextStyle(inherit: false)`**: In `TextStyle`, `IconStyle`, and nested `XStyle` objects, `null` exclusively means "inherit from preceding rules," so a later rule cannot clear a sub-property that an earlier rule already set back to `null`. For `TextStyle` specifically, its `inherit` field exists solely to serve `DefaultTextStyle` / `TextSpan` tree inheritance and is not a style property in the rule chain. Therefore, the engine **ignores `inherit: false` during rule merging** (always merging non-null sub-properties rather than treating `inherit: false` as a signal to wipe out preceding properties; in debug mode, passing a literal with `inherit: false` in a rule emits a diagnostic warning), and uniformly sets `inherit` to `false` on the final resolved `TextStyle` output of a component field (ensuring the resolved result is a self-contained style immune to accidental outer `DefaultTextStyle` pollution, while preventing `TextStyle.lerp` from throwing when `inherit` differs between endpoints).
   - **`Patchable` requires public getters to fully reconstruct the declared type (custom subclass identity is not preserved)**: When the engine executes `.parts(...)`, it reads the public getters from the value produced by preceding rules, replaces the specified components, and reconstructs the declared type itself. Consequently, if a user passes a custom `class MyInsets extends EdgeInsets` into an `EdgeInsets` slot and a subsequent rule applies `.parts(horizontal: ...)`, the resulting instance will be the base `EdgeInsets` class. This is documented as an explicit contract of `.parts`.
4. **Open leaf-level trade-off: whether to make `EdgeInsetsGeometry` `Patchable` (Option A vs. Option B)**:
   On the concrete class `EdgeInsets`, all four components (`left`, `top`, `right`, `bottom`) are public getters, directly supporting `.parts(left:, top:, right:, bottom:, horizontal:, vertical:)` (with an `assert` catching cases where `horizontal` is passed alongside `left` or `right`). In `material_ui`, however, 21 theme files declare their `padding` field as the abstract base class **`EdgeInsetsGeometry`** (only 4 places declare `EdgeInsets` directly, and a large-scale codebase survey shows that roughly 11% of button `padding` arguments pass `EdgeInsetsDirectional`). On `EdgeInsetsGeometry`, all component getters (`_top`, `_start`, etc.) are private to `flutter/painting`, and externally subclassing `extends EdgeInsetsGeometry` throws a `NoSuchMethodError` at runtime when calling `==`, `add`, or `horizontal`. In practice, the only valid runtime instances are the three internal models inside `painting`: `EdgeInsets`, `EdgeInsetsDirectional`, and the private class `_MixedEdgeInsets` produced when adding or subtracting the two. There are two options to weigh here:
   - **Option A (Conservative, zero framework changes)**: Support `.parts` only on the concrete class `EdgeInsets` and keep `EdgeInsetsGeometry` as `Atomic` (replaceable only as a whole). The advantage is zero changes to the Flutter framework; the downside is that most `padding` fields in Material cannot use `.parts`.
   - **Option B (Add a static projection helper function in `flutter/painting`)**: Because only code inside `painting` can read the components of the private `_MixedEdgeInsets` class, a static projection function can be added in `painting` that branches across those three internal models (if it encounters an unknown marker subclass from a community package using `implements EdgeInsetsGeometry`, it triggers an `assert` in debug mode and idempotently returns the previous value unchanged in release mode). For `.parts` parameters on `EdgeInsetsGeometry`, **only the four direction-agnostic parameters `top`, `bottom`, `vertical`, and `horizontal` are exposed** (where setting `horizontal` sets both left and right while clearing `start` and `end` on mixed values; `left`, `right`, `start`, and `end` are not exposed to avoid counterintuitive mixed stacking when setting `left` on an `EdgeInsetsDirectional`). The trade-off is adding one public static function to `flutter/painting`.

## 6.4 Code Generation Architecture and Multi-Widget Shared Rule Mechanism

### Single Source of Truth and Checked-In Generated Files

With build-time code generation, component authors no longer need to manually maintain and synchronize boilerplate across 9 different places as they did in the past:
- **Single source of truth definition**: In a single definition file, the component author declares only: (1) the component's list of fields and their types; (2) the condition dimension enums and boolean states supported by the component; and (3) the component's default rule table.
- **Three categories of generated artifacts**: After completing static exhaustiveness checks and region simplification, the generator automatically produces: (1) `XStyleSpec` and `XStyle` (including sub-property merging and `lerp`); (2) the field enum `XField`, source classes `XSource` / `XColorSource`, and callback view `XView`; and (3) the condition class `XWhen` and rule class `XRule` (including `.when`, `.always`, `.whenAny`, and region constructors for all multi-region fields). Note: flat parameters on widget constructors are never auto-generated; instead, component maintainers hand-pick the most commonly used entries from the generator's partitioned rule regions as widget constructor parameters and map them to call-site rules internally using the generated region constructors.
- **Checked-in generated files**: All `.g.dart` generated files are committed directly into the `cupertino_ui` and `material_ui` repositories and published with the packages, so **downstream application developers never need to install or run any code generation tools**. The generator includes a built-in package-level name collision check to prevent a generated `<Component>Style` from clashing with existing classes in `painting` or `widgets` (such as `TextStyle`).

### Sharing a Single Rule Set Across Multiple Widgets: Appearance-Scoped Rule Subclasses

In `cupertino_ui`, buttons of different appearances are already a single `Button(appearance: ...)` widget. In `material_ui`, however, there are four separate widget classes—`ElevatedButton`, `FilledButton`, `OutlinedButton`, and `TextButton`—covering five appearances in total (including the named constructor `FilledButton.tonal`). While keeping these widget classes and their public APIs unchanged, they share a single set of `appearance`-aware rule types at the styling layer: `CommonButtonStyle`, `CommonButtonRule`, and `CommonButtonWhen` (see Section 8.2 for the rationale behind sharing).

When multiple widgets share the same underlying rule set, API discoverability becomes important: a developer who writes `OutlinedButton(...)` in their UI will naturally look for `OutlinedButtonRule` when configuring styles in a theme.

If `OutlinedButtonRule` were merely a type alias (`typedef OutlinedButtonRule = CommonButtonRule`), writing `OutlinedButtonRule.always(...)` would still modify all five button types, violating the expectation set by the class name. Instead, the generator emits a **genuinely appearance-scoped rule subclass** for each appearance: `ElevatedButtonRule`, `FilledButtonRule`, `FilledTonalButtonRule`, `OutlinedButtonRule`, and `TextButtonRule`.

```dart
final class OutlinedButtonRule extends CommonButtonRule { ... }
```

The mechanism works as follows:
1. **Underlying scope restriction and condition intersection**: The superclass `CommonButtonRule` holds a private nullable field `_scope` (of the appearance enum type `CommonButtonAppearance?`). The superclass's own constructors set `_scope` to `null`, while subclass constructors pass their corresponding appearance via a private superclass constructor `super._scoped(CommonButtonAppearance.outlined, ...)`. When converting rules into internal engine rules during chain construction, if `_scope` is non-null, the engine intersects each condition of that rule with `appearance: {outlined}` (conditions that do not constrain appearance automatically gain this appearance restriction; sets containing this appearance narrow down to only this appearance; and conditions excluding this appearance are dropped, triggering an `assert` in debug mode if all conditions are dropped). Performing this intersection during chain construction rather than inside the constructor is necessary because a `const` constructor cannot dynamically rewrite a condition list passed to `.whenAny` at compile time.
2. **Constructors provided on the subclass**:
   - **`.when(...)`**: Accepts the same parameters as `CommonButtonRule.when`, except that the `appearance` parameter is removed (passing `appearance` is a compile-time error);
   - **`.always(...)`**: Takes effect only under the appearance corresponding to that subclass;
   - **`.whenAny(...)`**: Accepts a `List<CommonButtonWhen>` and narrows the appearance scope during chain construction according to the intersection rules above;
   - **Region constructors**: Include only the regions for that field under the subclass's single appearance, **with the appearance prefix stripped from parameter names**. For example, the superclass's `CommonButtonRule.side(outlinedIdle:, outlinedFocused:, outlinedDisabled:)` becomes `OutlinedButtonRule.side(idle:, focused:, disabled:)` on the subclass, and the superclass's `outlinedAnyState:` becomes `OutlinedButtonRule.backgroundColor(anyState:)`. For fields like `foregroundColor` that share the same partitioning across all appearances, both the superclass and the subclass generate `.foregroundColor(enabled:, disabled:)`, where the superclass applies to all five buttons and the subclass applies exclusively to `OutlinedButton`.
3. **Narrowing the instance `rules:` parameter type**: The parameter type of `OutlinedButton(rules:)` is narrowed to `List<OutlinedButtonRule>`. This makes the IDE's type hints match the widget name directly while preventing developers from passing rules meant for other appearances into an `OutlinedButton` instance at compile time.
4. **Precedence and binary size overhead**: The precedence of an `OutlinedButtonRule` in the rule chain is determined purely by its position in the list, identical to writing `CommonButtonRule.when(appearance: {.outlined}, ...)` by hand. Each appearance subclass contains only forwarding constructors, occupying just **61–80 bytes** in the AOT binary when referenced and tree-shaking out completely when unused. By convention, developers use the specific subclass when modifying a single appearance and `CommonButtonRule` when modifying multiple or all appearances at once.
